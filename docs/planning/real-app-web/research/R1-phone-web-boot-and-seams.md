## 2. Seam map

Reading guide. "Web impl" = what the **installed** version ships. "Treatment": AS-IS (works unchanged), SMALL (a few dozen lines), LIFT (reuse the demo's browser code), SIM (simulated and labelled), N/A (not available, say so). "Seam" = the narrowest replaceable unit. **Two kinds of seam are needed**, because Metro platform extensions (`foo.web.ts` beside `foo.ts`) only apply to files in the repo, not to packages in `node_modules`:
- **(F)** a repo file gets a `.web.ts(x)` sibling;
- **(P)** a package-level alias in `metro.config.js` (`resolveRequest`, web only) pointing at a stand-in under e.g. `web/shims/`. Used where one package is imported from many files, so the 17/6/4 call sites stay untouched. Verified working for four packages in this build.

## 4. Risks and unknowns

1. **Silent no-ops are the main hazard**, not crashes: `Alert.alert` (96 sites), `expo-print` (`window.print()` of the host page, returns undefined), `expo-sharing` (`navigator.share({url})` with a local URI), date picker (no sheet), WebView ("does not support this platform"). Under the "never a fake success" rule each needs an explicit stand-in; list above.
2. **Encryption posture changes.** On web the case DB and ZIP password live in plaintext browser storage; the phone code enforces the opposite by refusing to boot without SQLCipher. The guard bypass and any on-screen/PDF claim ("AES-256 at rest", "protected export") need honest web wording. Product decision for the owner.
3. **Secrets and telemetry in a public bundle.** The whole `app.config.js` is inlined; production Sentry is enabled with the real DSN; `extra.timeApiKey` / Supabase env would be public. Export must run with those env vars empty and Sentry stubbed.
4. **Browser coverage not tested.** Only Chromium headless. OPFS `createSyncAccessHandle` (used by the `AccessHandlePoolVFS` worker) needs Safari 16.4+ and is the make-or-break for iOS Safari visitors; Firefox and private-browsing storage limits unknown. R2 owns storage depth.
5. **PDF output is an open design problem.** The phone pipeline is HTML -> PDF **file** -> share/zip/attach. Browser options: HTML-only + print dialog, or a client-side PDF library. Drives the print, preview, share and zip stand-ins together.
6. **Native regression risk of adding `metro.config.js`, `react-dom`, `react-native-web`, `@expo/metro-runtime` and `web/` shims to PHONE `main`.** I did not run a native build or the jest suite. Every hook I used is guarded by `platform === 'web'`, and `getDefaultConfig` is what Expo applies when no config exists, so the risk looks low but is unverified. Expect `expo-doctor` / `check:invariants` / lint rules (persona and import-barrel rules) to need review for the new `web/` folder.
7. **Not exercised:** Map tab with data (rnmapbox replacement), bottom sheet gestures, swipe-to-delete, export/PDF/ZIP/GeoJSON flows end to end, photo capture, real audio recording, `Share.share`, `expo-image`/`expo-audio` playback from stored files, light/dark switch, reload mid-wizard, the dev server (`expo start --web`) and Fast Refresh.
8. **Bundle weight.** 1.8 MB brotli JS + 8.5 MB assets; one 1.66 MB embedded string (`case-map.vendor.ts`) used only by the offline map export; `MaterialCommunityIcons.ttf` 1.3 MB for one icon; splash mp4 5.5 MB; Sentry 0.8 MB; no route-level code splitting. All fixable later; none blocks.
9. **Evidence discrepancy.** The shared context says `.design-sync/NOTES.md` "records what broke" under react-native-web. On `main` that file is the older tokens-only version that *rejects* an RNW port. The relevant notes are on the unmerged branch `origin/chore/design-sync` (4 commits ahead; read via the clone). My independent run reproduced its input-stacking and date-picker findings.
10. **Cosmetic:** tab-bar clipping, missing `Layout.headerPadding.web`, missing ShareTechMono web font, `Animated useNativeDriver` warning.

## 5. Recommendations

1. **Proceed with building the real app for web via `expo export -p web`, output `single`, hosted under `/app/` with `experiments.baseUrl: '/app'`.** Boot, SQLite persistence, navigation and all wizard screens are proven. Confidence: **high**.
2. **Use two seam mechanisms, not one.** `.web.ts(x)` siblings only for repo-owned modules (about 7). For `node_modules` packages add a **package alias table in a new `metro.config.js`** (web only, resolver hook matching the *resolved* file for RNW internals) pointing to a single `web/shims/` folder. This leaves 17 + 6 + 4 + ... call sites untouched and keeps all stand-ins reviewable in one place. The brief's "`foo.web.ts` next to `foo.ts`" cannot replace a package. Confidence: **high** (verified for four packages).
3. **Order of work, by what unblocks the most:** (a) base layer: `metro.config.js` (wasm + alias table), deps, `public/index.html` CSS fix, real `Alert` dialog, FS and secure-store stand-ins (R2), DB guard bypass, rnmapbox + Sentry stubs -> case/location/wizard usable; (b) viewers: WebView iframe, `DateTimePicker` web branch, print/share/zip decision; (c) capture: vision-camera shim, Tesseract OCR, verify audio and expo-camera; (d) map (`CaseMapView.web.tsx`); (e) time-sync simulation; AI provider; splash/biometric polish. Confidence: **medium-high**.
4. **Make `Alert.alert` the first stand-in.** Highest call-site count, silent failure, blocks case creation. Best seam: replace RNW's `Alert` module (one alias) with a promise-driven dialog rendered inside the phone frame. Confidence: **high**.
5. **Disable Sentry on web and export with empty `TIME_API_KEY`/`SUPABASE_*`/token env** (set only the URL-restricted public Mapbox token). Confidence: **high**.
6. **Keep the biometric flow as the app already degrades it** (no gate on web; `BiometricsUnavailableScreen` if a visitor turns app lock on) and shorten the 8 s splash on web; add a labelled simulated scan only if the owner wants the Face ID moment. Confidence: **medium** (owner preference).
7. **Treat "encrypted at rest" as a labelled difference on web** and decide wording before shipping; keep the cipher guard intact for native. Confidence: **high** that it is needed, **low** on exact wording.
8. **Pilot Safari/iOS early** for the OPFS worker path before investing in the other stand-ins. If OPFS fails there, the fallback is expo-sqlite's in-memory VFS (loses persistence) or a different engine; this is the largest unknown. Confidence: **medium** that it works (wa-sqlite AccessHandlePool is supported in Safari 16.4+, not tested here).
9. **Decide the PDF strategy before the print/share/zip stand-ins** (HTML + print dialog like the demo, or client-side PDF bytes). Confidence: **high** that this is the central open question.
10. **Make the rnmapbox replacement a single `CaseMapView.web.tsx`** (contract is a clean props + ref API) lifted from the demo's `MapCanvas.tsx`, and move the root `setAccessToken` call behind a tiny helper. Do not try to complete rnmapbox's own web build (it has no layers). Confidence: **high**.

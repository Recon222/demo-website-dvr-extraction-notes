## Method

1. **Tier A first.** Every phone token-family change (phone §1) and every shared recipe (phone §2 headings) becomes one row. For each, locate where the demo carries that value today — the shared seam if one exists (demo §1/§4), otherwise every inline copy with its census count (demo §2).
2. **Tier B second.** Every phone surface the phone inventory marks CHANGED (phone §3.1) becomes a row keyed to **both** join keys: the v1 matrix row `#` and the `ui-mapping` doc. Each Tier-B row names the Tier-A rows it consumes, then only what is *surface-specific beyond the recipes*.
3. Surfaces the phone marks UNCHANGED (phone §3.2) get one compact COMPLETE table — do not re-open them.
4. New phone components with no demo counterpart (phone §4) get MISSING rows.
5. Demo-only surfaces (demo §7.1) get an N/A table with a per-surface ruling ask.
6. Classify → size → bucket into phases.

**The one structural fact that shapes everything.** The demo has **six** places a visual value can live (demo §1), and the bottom one holds **1,144 colour occurrences across 136 files** (demo §2.2). Roughly **one in three** is a hand-typed copy of a value that already has a token name three directories away (demo §2.4). The phone, meanwhile, spent fourteen PRs collapsing eight card families into one tier system. So most Tier-A rows are not "change a value" — they are **"build the seam, adopt the consumers, then change the value once."** That is what MISSING-SEAM means below.

## Status legend

Adapted for a style port. The v1 legend (COMPLETE/PARTIAL/STUB/MISSING) described whether a *surface existed*; this one describes whether a *value or recipe matches*.

| Status | Meaning |
|---|---|
| **COMPLETE** | The demo already renders what the phone renders at `main`. No work. |
| **DRIFTED** | The demo has the value/recipe in a real seam, but the value differs. Work = change the seam. |
| **MISSING-SEAM** | The demo renders the right *idea* with the value scattered across consumers. Work = build the shared recipe, adopt the consumers, then change the value once. |
| **MISSING** | The surface, component or token has no demo counterpart at all. |
| **DEMO-BETTER** | The demo's version is ahead; do not regress it toward the phone. |
| **OUT-OF-SCOPE** | Owner-excluded, or phone-only mechanics with no web analog (phone §6). |
| **OPTIONAL** | Defensible either way; a flourish, not parity. |
| **N/A** | Demo-only surface with no phone counterpart. Needs an independent ruling, not a port. |

**Effort** is relative package size for sequencing and model-tier choice, **not calendar**: **S** one seam or one value · **M** a recipe plus its consumers · **L** a new component or a rewrite · **XL** none in this port. Wall-clock is agent time, and the parallelism tax here is ~2s (`pnpm install --prefer-offline`, shared pnpm store) — so the sequential-vs-parallel call per phase is about **file contention (§6.1)**, never about calendar.

**Phases** are `U0`…`U8`, defined in `01-master-ui-parity-plan.md` §5.

### D1 — Phone-side verification on Windows: how do we know the port matches?

## C.3 — The standing recipes the ratios produced

Four rules the campaign arrived at empirically. **These are more portable than any single number.**

1. **Stop using red as text.** `colors.error` as normal-size text measures **4.40 dark / 3.76 light**, and *"nothing in the palette clears 4.5:1 in both themes with the hue intact."* The answer is not a better red — it is **severity on the icon (3:1 non-text floor), text in `colors.text` (17.74 / 13.30)**. Adjudicated-closed `P8-DEF-A`; *"the single most portable recipe in the whole ledger."* The demo has **six error-text reds** (`#ff4757`, `#ff6b78`, `#ff6b7a`, `#ff7a85`, `#ff8a93`, `#ff8a94`) doing exactly what this rule forbids.
2. **`onPrimary`/`onError` pair with the deep shade, never the flat mid-tone.** Carved out and *fine* as non-text marks at 3.73: checkboxes, indicators, bounding boxes, capture buttons.
3. **Measure a token on the ground it actually lands on, not on the flat card.** DEF-UI-014: `textSecondary` measured 4.41 on `card` but **3.97** nested inside a glass section — *"size the fix against 3.97, not 4.41."*
4. **The border is decorative only when the fill, the icon and the text each carry the severity independently** (`DEF-B`). That is why `Banner`'s border can measure 1.93 and still be correct, and why a sole-boundary input border at 1.26 is not.

## C.4 — Porting `palette-contrast.test.ts` as a demo test

**Recommendation (P0 deliverable):** port it, dark half only, as `features/demo/ui/__tests__/palette-contrast.test.ts`.

What ports: the WCAG 2.1 relative-luminance helper, `flattenOver` (A53) so translucent stops are measurable, the `DARK_GROUNDS` stack construction, the CIE76 ΔE helper, and rows 4, 5, 8, 10, 12, 13, 16, 18, 21, 22–25, 30, 31, 33, 34, 36–40 above. What does not: every light row, and the `Colors`-module deep imports (the demo's equivalent is `glass-tokens.ts` + `input-theme.ts` + the new tier module).

**Two structural pins to copy, not just the numbers:**
- **Pin the ratio at the constant, not at a consumer** (`:265-274`) — or a mutation back to a failing value stays green.
- **Bound `recessed` two-sided and per-stop** (`:343-374`) — "too flat" and "too deep" are both bugs.

**This test plus the drift guard (at its current anchor set) is the port's mechanical gate.** The drift guard catches *value drift against the phone*; the contrast test catches *legibility drift within the demo*. Neither catches the other's failure mode, and neither catches the two ΔE-shaped defects PR #125 found on a device — which is what D1 is about.

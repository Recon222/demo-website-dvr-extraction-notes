## 1. REFUTATIONS — verified against source, first

Eight claims in the plan, the matrix, the brief and U5.1's successor note did not survive contact
with the phone or with the tree. Each carries `file:line` and each is **pinned**, so a later "fix"
back toward the doc must red rather than pass quietly.

### R1 — `LocationRow` indicates selection NOT AT ALL. "The fill stays, the border tints" is refuted

The plan's U5.4 row says: *"delete the `borderLeft:'4px solid accent'` … draw uniform four-sided
borders. Keep **"selection ADDS, never swaps"** — the fill stays, the border tints."* That is
correct for `CaseMapPicker`. It is **wrong for `LocationRow`**, where the phone removed the
treatment outright. `map-view/components/LocationRow.tsx:51-56`, verbatim:

> *"The border is UNIFORM. It used to reserve a 4px left edge and tint it with the status colour
> when selected, which left the unselected rows reading as though their left border were missing —
> the reserved edge was painted `transparent`. **Selection is not indicated here at all now:
> tapping a row opens that location's own sheet, which is the signal.**"*

`isSelected` survives only as `accessibilityState={{ selected }}` (`:79`).

**And in the demo the treatment was provably dead paint.** `MapScreen` writes `selectedId` and
`sheetMode` only in PAIRS, at all three write sites — `(id, 'detail')` `:264-265`,
`(null, 'list')` `:197-198`, `(null, 'list')` `:272-273` — so `selectedId !== null` implies
`contentMode === 'detail'` (`:248`), and the list that would render a selected row is unmounted
whenever a selection exists. The `${color}50` border and `${color}14` fill could never render.

Ported as the phone ships it; the prop survives as `data-selected` (the repo's own idiom, already
on `CaseMapPicker`'s rows). Pinned by comparing the **whole `style` attribute** between the two
states, because an assertion on one state alone stays green when someone re-tints the other.

### R2 — "Status chips → the badge recipe" is wrong for BOTH map surfaces

The U5.4 row says *"Status chips → the badge recipe"*, which reads as `tokens/status.ts`'s
`statusBadgeStyle`. **`grep -rn CaseStatusBadge src/features/location/map-view/` returns one
COMMENT and no import** (`constants/index.ts:55`). All three map chips are hand-rolled and none
of them matches `CaseStatusBadge`'s geometry:

| surface | phone | `statusBadgeStyle` |
|---|---|---|
| `LocationRow` type chip (`styles.typeChip` `:338-349`) | radius `sm` (4), pv 1 / ph `xs`, **no border**, uppercase | radius `lg` (12), `BADGE_PADDING`, 1px border, no uppercase |
| `LocationDetailCard` status badge (`styles.statusBadge` `:847-866`) | radius `control` (10), pv `xs` / ph `sm`, **+ a 6px dot**, ls .3 | radius `lg`, no dot, weight 600 |
| `SheetHandle` badge (`styles.badge` `:164-181`) | radius `md` (8), pv `xxs` / ph `xsm`, **+ a 5px dot** | radius `lg` |

What A70 actually publishes is **two lookups, one contract** — and `tokens/status.ts:19-23` says so
in a table: *"a badge, chip or banner … → `severityTone()`"*, *"a bare dot … → `.accent`"*. All
three surfaces take `severityTone()` with the phone's own geometry. `statusBadgeStyle` is
`CaseStatusBadge`'s recipe, and importing it here would invent a contract the phone does not hold.

## 6. Deferral PROPOSALS (house format — the aggregator decides and writes)

**D-1 · `MapCanvas`'s retry button is the last hand-rolled button in `screens/map/`**
- **Source:** U5.4 implementation. U5.1's successor note anticipated it: *"`SHEET_COLORS.accent`
  can go when the retry button folds onto `buttonStyle`."*
- **What:** `MapCanvas.tsx:122-135` (`retryStyle`) paints a filled control by hand (`background:
  SHEET_COLORS.accent`, `color: colors.onPrimary`), and `SHEET_COLORS.accent` exists solely to
  feed it. Every other button in `screens/map/` now goes through `buttonStyle`. Folding it in
  deletes the key and takes the map island to zero local button recipes.
- **Why deferred:** `MapCanvas.tsx` is in **no** U5 package's Files column — U5.1 touched it only
  for the token re-point (its deviation 2), U5.2 owns `MapControls`/`MapScreen`, U5.3 creates
  `MapFiltersSheet`, and U5.4's row lists the sheet surfaces. Opening a 671-line file with a live
  `mapbox-gl` boot sequence for one button is exactly the scope creep §6.1 serialises against, and
  U5.2 is running concurrently.
- **Trigger:** **the first package that opens `MapCanvas.tsx` for anything beyond a token
  re-point.** If no W3 package does, it falls to **U8.2's banned-literal guard closing pass**,
  which already owns the last sweep over `ui/**` — the same trigger family as D-2. If U8.2 lands
  without it, the entry is a dropped finding.

**D-2 · The two demo-only map surfaces are still 100% hardcoded**
- **Source:** U5.4 implementation; demo inventory §7.1 (both are marked demo-only), §3's
  per-file blocks.
- **What:** `map/CallConfirmSheet.tsx` (`rgba(28,32,40,0.96)` — "an iOS-native grey found nowhere
  else"; `#cdd9e6`; `#34c759`, a lowercase spelling of a pin colour; `#4ba3d4`;
  `rgba(255,255,255,0.12)`; and `zIndex: 48`, "a standalone magic number outside every named
  scheme") and `map/DemoNotification.tsx` (`rgba(20,30,46,0.96)`, `rgba(75,163,212,0.4)`,
  `#e7eef6`, `zIndex: 60`). D12 rules demo-only surfaces INSIDE the frame "follow" the palette,
  so both should move.
- **Why deferred:** `partner-legwork-w3.md` §S2 rules **"Nothing owed"** on `CallConfirmSheet`
  after U4.4's scrim edit, and no U5 row names either file. More substantively, `CallConfirmSheet`
  deliberately mimics the **iOS system** action sheet, and D17 is the standing precedent for
  freezing that class of chrome (it keeps iOS system red `#FF3B30` on purpose) — so "follow" here
  is a design ruling the owner has not made, not a transcription U5.4 can perform. The z-index
  pair is D14, explicitly out of scope.
- **Trigger:** **U8.2's banned-literal guard closing pass**, which is where the retired-ramp
  widening (U5.1's D-2) also lands — at that point both files' literals become guard rows and the
  owner's "follow or freeze" call has to be made rather than deferred. Whichever way it goes, it
  is recorded there.

**D-3 · `glass-tokens.ts:307-309` documents a shorthand the card fragments no longer carry**
- **Source:** U5.4 implementation, R8 above.
- **What:** `glassWell`'s docblock says *"`glassCard` / `glassCardNested` above still carry a
  `border` SHORTHAND — that is W1's shape and the ruling's §4 item 1 assigns changing it to that
  seat, not to this one."* Both fragments are longhands-only (`:214-224`, `:259-269`) and
  `glass-card-recipe.test.tsx:248-263` pins the absence of all three shorthand keys on both. The
  note is a leftover from before W1's rider landed.
- **Why deferred:** `ui/glass-tokens.ts` is §6.1's **hottest file** (U0.1, U0.2, U0.3, U1.1, U1.2,
  U2.2, U8.2) and U5.4 is not among its owners; editing it from a W3 package to fix a comment is
  the cross-lane write §6.1 exists to prevent.
- **Trigger:** **U8.2**, the only remaining package that opens `glass-tokens.ts` (for the
  banned-literal guard's closing pass). It is a three-line docblock edit with a test already
  proving the correct statement, so there is no cost to doing it there — and a reviewer following
  the stale note would conclude `{ ...glassCard, border: X }` is discouraged rather than a live
  defect the lit-edge ruling was written to kill.

## 11. Two likely defects (where I would look first)

1. **The peek detent is frozen at 116px and the handle's content height moved — in both
   directions.** `SHEET_HEIGHTS = [116, 340, 560]` is on demo §0.10's may-not-change list, tuned
   to the 378×786 frame. The handle now adds a 2px accent strip and takes the count line 16 → 18,
   while the pill row loses 6px (`paddingBottom` 10 → `spacing.xs`) — roughly −3px net, which is
   fine. **The risk is the badge row.** Its gap went 6 → 8 and its labels 11px → 12px, so three
   non-zero statuses are ~10px wider than before against a 378px screen; `flexWrap` will take them
   to a second line sooner, and the sheet is `overflow: hidden`, so the second line clips instead
   of scrolling. **No test can see this**: `vitest.setup.ts` stubs `ResizeObserver` as a no-op and
   jsdom lays nothing out (demo §0.8). Check it on the device pass with `started`, `working` and
   `complete` all non-zero and long labels.
2. **`LocationRow`'s `selected` prop is now paint-free, and the invariant that makes that safe
   lives in a different file.** The prop is still threaded from `MapScreen` → `LocationList` →
   `LocationRow` and reaches only `data-selected`. The next reader will find a selection prop with
   no selection cue and "restore" one — reintroducing precisely what `7df5148b` removed. Two
   things guard it and both are soft: the pin compares whole `style` attributes between the two
   states (a reviewer could read that as a change-detector and weaken it), and R1's dead-paint
   argument rests on `MapScreen` keeping `selectedId !== null ⟺ contentMode === 'detail'` across
   all three write sites. **U5.3 adds host state to that same component.** If a future edit ever
   leaves the list mounted with a selection — a filters sheet that clears `sheetMode` without
   clearing `selectedId`, say — the row silently becomes the one surface in the app whose
   selection is invisible, and nothing reds.

### R-1 — §4.3's case law prescribes a remedy that does not work. (CHANGED WHAT I BUILT — and what I wrote in the module)

> Plan §4.3, verbatim: *"**When overriding a fragment that carries `borderTopColor`, override
> `borderColor`, never `border`.**"*

**False, and measured.** `border-color` is itself a four-side shorthand. In this repo's jsdom
(29.1.1, via `cssstyle`), writing either one after the longhand resets all four sides:

```
A  style.border = '1px solid rgba(28,78,132,0.5)'; style.borderTopColor = '<h>'; style.border = '1px solid #ff0000'
   -> borderTopColor === 'rgb(255, 0, 0)'
B  ... same two, then style.borderColor = '#ff0000'
   -> borderTopColor === 'rgb(255, 0, 0)'   AND borderRightColor === 'rgb(255, 0, 0)'
```

Both are also true in real CSS — `border-color` expands to the four longhands, full stop. Probes
**P2 (KILLED)** and **P3 (KILLED)** are the two halves of this at a real consumer.

**Built:** the loop pin catches BOTH shapes (it reads `borderTopColor` *and* the three side colours,
plus a per-consumer count), and `glass-tokens.ts`'s docblock states the correct remedy: *"Override
`borderColor` AND re-set `borderTopColor`, or do not override at all."* **The plan's §4.3 bullet needs
its second sentence corrected** (§9 corrections owed). Nothing in-tree relies on the wrong version —
no `glassCard` consumer overrides either key today (measured across all ten sites) — so this is a
latent trap, not a live defect.

### Design decisions, each with the alternative rejected

1. **`GLASS.shadowCard` as a token, not a literal in the fragment.** *Rejected:* the literal the U1.2
   row spells. A44 is a MISSING-SEAM row and `ExportCaseCard:133` was already its second consumer
   (R-3). One token, two consumers, one `BANNED` entry, zero duplication.
2. **The lit edge as `borderTopColor`, not a 1px absolute child.** *Rejected:* transcribing the
   phone's two-element structure. That structure exists because RN cannot colour one border side; the
   web can, and `conventions.md` says to. A child element would also break `overflow` and stacking at
   the five consumers that already use `position: relative`.
3. **No `padding` in either fragment.** *Rejected:* `conventions.md`'s `padding: var(--spacing-md)`.
   Six different lifted paddings across ten sites; demo §0.4.
4. **No `glassCardDiag` fragment.** *Rejected:* giving `CasesScreen`/`DashboardScreen`/`ExportCaseCard`
   the full four-part composition with the 135° gradient. It reads like the obvious completion of
   U1.2 and it is **out of scope in a way that would have hurt**: `gradientCardDiag` has **eight**
   consumers, several of them nested ROWS at radius 8 (`CasesScreen:240`, `DashboardScreen:201`) and
   several in files U3.4/U5.4/U7 hold open. Deferral **D-1** proposed instead, with a trigger.
5. **`nestedCard` takes no elevation shadow.** R-5, probe P14.
6. **The loop pin locates card surfaces by the tier-composed gradient, minus `<button>`s.**
   *Rejected:* a `data-*` marker in production (a test artefact in shipped DOM), and per-component
   testid queries (nine bespoke selectors that drift). The one button painting the card gradient is
   `AudioRecorderScreen.tsx:481`'s transport pill at radius 21 — not a card, and U7.2's DEF-UI-008
   carve-out keeps it on its own gradient deliberately. Written at the filter, so a future card on a
   `<button>` is an explicit edit rather than a silent miss.
7. **Per-consumer card COUNTS in the loop pin.** *Rejected:* asserting only over whatever the filter
   found. An override that erases the border changes the side colours the filter reads, so the
   offending element would drop OUT of the set and a shape-only assertion would pass vacuously. Probes
   P2/P3 are killed by the count, not by the colour assertion.

### The three SURVIVED results, and what I did about them

**P11 / P13 — I wrote a tautology and mutation testing caught it.** `NESTED_GRADIENT` was
`normGradient(glassCardNested.background)` and `CARD_GRADIENT` was `normGradient(GLASS.gradientCard)`
— **both read off the very object under test**. Re-pointing the fragment at a different tier, or
transposing A33's swapped stops, moved the expectation with the mutation and the whole file stayed
green while `/demo` painted the wrong tier. The locator was tautological too, so the per-consumer
count could not notice either.

Both now compose from `tokens/glass-tiers.ts` through a local `composed(tier)` helper, so the two
sides of every comparison come from **two different modules**. Re-probed at `97ca9eb`: **P11r and P13r
both KILLED**, and **P5r** (added because the same reasoning applied to the card locator) **KILLED**.
This is the highest-value thing in the package: without the probe, U1.3's six new "behavioural" pins
would have been decoration.

**P7 — a documented split, not a defect.** The loop pin asserts
`boxShadow === \`inset 0 1px 0 ${tier.card.innerShadow}, ${GLASS.shadowCard}\``. The first half is
cross-module and falsifiable; the second is read from the same module that produced it, so an
`8px → 9px` drift is invisible **there**. It is not invisible: **P7b KILLS it at
`glass-tokens.test.ts`'s literal shape pin.** The line's real claim is the two-part COMPOSITION — that
both halves reach the DOM, in that order — and **P6 KILLS** the removal of either half. Spelling A44's
literal in a second file would make a legitimate re-base a two-file edit and buy no falsifiability.
Both facts are written at the assertion so a reviewer does not have to re-derive them.

And the pair cannot be transcribed: CSS collapses two facing sibling margins to the larger, so
`marginBottom: 16` + `marginTop: 8` renders **16** on the web and silently loses 8px. Resolved
by summing onto the header and documenting it in the component docblock — see §3, deviation D-1.

what the phone paints (`TextInput.tsx:128`) — and matrix §C.3 rule 1 forbids exactly that, by
name. See §3, deviation D-2, with the measurements.

## 3. Deviations, with justification

### D-1 — the header's bottom margin is the phone's TWO values, summed onto one node

**What:** header `marginBottom: spacing.md + spacing.sm` (24), and no content wrapper.
**Phone:** `header.marginBottom = spacing.md` (16, `:182`) **and**
`content.marginTop = spacing.sm` (8, `:198`).
**Why:** RN does not collapse margins; CSS collapses facing sibling margins to the larger. The
verbatim transcription renders **16**, silently losing 8px against the phone's 24 — the class of
"faithful-looking and wrong" defect §4.2 warns about. Summing renders the phone's geometry with
one node instead of two.
**Known ceiling, stated in the docblock:** a first child carrying its own `marginTop` would
collapse INTO this 24 rather than adding to it. No consumer has one — `Field`, `SelectField` and
`DateTimeField` all lead with `marginBottom`. A future consumer that does needs the wrapper back.

### D-2 — `Field`'s error line: severity on the ICON, message in `colors.text`

**What:** the message takes `colors.text` and a 16px `Banner`-shaped alert-circle in
`colors.error` sits before it.
**Phone:** `color: colors.error` on the text (`TextInput.tsx:128`, `errorText:184-186`).
**Why:** matrix **§C.3 rule 1**, adjudicated-closed as `P8-DEF-A` and described there as *"the
single most portable recipe in the whole ledger"*:

> *"Stop using red as text. […] The answer is not a better red — it is severity on the icon (3:1
> non-text floor), text in `colors.text`."*

The same paragraph names **`#ff6b78`** — the exact value this line carried — among the six
error-text reds the demo ships *"doing exactly what this rule forbids"*. The plan's own U6.4b row
applies the identical treatment to `SyncStatusCard`, so this is the campaign's standing recipe,
not a local invention, and D20 puts presentational composition in scope where a package's row
specifies the surface.

**MEASURED**, worst / best over the dark grounds `palette-contrast.test.ts` composites
(`background`, both `card` stops, both `nestedCard` stops over `background`):

| Colour | Worst | Best | Floor |
|---|---|---|---|
| `#ff6b78` (was) | **3.84** | 5.34 | 4.5 text — fails |
| `colors.error #ff4757` (the phone's) | **3.16** | 4.40 | 4.5 text — fails worse |
| `colors.text` (now, the message) | **9.56** | 13.30 | 4.5 — clears |
| `colors.error` as the ICON | **3.16** | 4.40 | 3.0 non-text (1.4.11) — clears |

So porting the phone's token verbatim would have **lowered** this line, and neither red clears
AA at any size. `4.40` is the same number §C.3 rule 1 quotes for `colors.error` as normal-size
text, which cross-checks the compositing.

The glyph is `Banner`'s `error` icon — the alert-circle the demo already reads as "error" at
`PickerStage`, `ImportModal` and `DemoErrorBoundary` — so a field error and a callout error are
the same mark. `aria-hidden="true"`, because the message inside the same `role="alert"` already
carries the text.

### D-3 — `hint` takes `textSecondary`, not the `textTertiary` its old hex names

`#7a9fc4` **is** `colors.textTertiary`, so "route through the palette" reads as `textTertiary`.
The phone paints `colors.textSecondary` (`TextInput.tsx:133`), and D5's rider bars new
`textTertiary` TEXT. Measured: `#7a9fc4` 3.81 worst (it sits on the documented 3.79 ceiling),
`textSecondary` 5.24 worst. Phone-exact and a contrast gain in the same move.

## 9. Two likely defects (asked for by the brief)

**Defect 1 — `overflow: 'hidden'` on `SectionCard` will clip the first thing that overflows it,
and nothing in the suite would see it.** It is faithful (phone `:159`) and inert today: every
current child is inside the card's 16px padding, and `Dropdown` / `DateTimeField` portal their
sheets out through `PhoneOverlayPortal`. But `css: false` in `vitest.config.mts` means jsdom
renders no layout at all, so a clipped popover, a cut-off focus ring, or a `position: sticky`
child that stops sticking would pass every test in the repo. The next component dropped into a
`SectionCard` that paints outside its own box is the one that finds this — and it will look like
that component's bug. **Watch:** any package adding an absolutely-positioned or overflowing child
to `CompletionScreen`, `DvrInfoScreen`, `ExportInfoScreen`, `SubmissionScreen` or
`TimeOffsetScreen`.

**Defect 2 — the empty-section collapse now runs on EVERY `SectionCard`, and
`Children.toArray` counts a rendered-but-empty child as a child.** The phone's guard has the
same property, so this is a faithful port of a sharp edge rather than a new one. Two shapes bite:
a section whose only child is a component that itself returns `null` (a `<RetentionView>` with no
scopes, say) still counts as one child and renders an empty titled box — the exact outcome the
guard exists to prevent; and conversely, a consumer that starts passing a string or a `<>…</>`
fragment changes the count in ways the call site cannot see. `DvrInfoScreen`'s "Retention"
section is the live candidate for the first shape: it hosts a placeholder today
(`empty-state.test.tsx:105` records *"the retention placeholder, inside a populated
SectionCard"*), so it is safe now and stops being safe the moment that placeholder becomes a
conditional. **Watch:** U6.4b, which opens `DvrInfoScreen`.

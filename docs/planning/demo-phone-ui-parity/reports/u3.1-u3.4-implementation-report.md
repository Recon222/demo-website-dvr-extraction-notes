## 1. REFUTATIONS — brief and spec claims that did not survive source

Ordered by consequence.

### R-1 · U3.1 adds EIGHT palette keys, not four (plan) and not two (U0.4). CORRECTED IN THE GUARD.

The plan's U3.1 row: *"CLOSING ACT — add the four status anchors (`success`, `successLight`,
`warning`, `warningLight`)"*. The brief's steer, from U0.4's P-3: *"U3.1 adds TWO keys, not four
(`success`/`warning`/`successDark`/`warningDark` already anchored) — verify"*. **Both undercount.**

The reason is structural, not arithmetic. Since review W0/F2, `PALETTE_KEYS` is no longer a chosen
subset: `rn-token-parity.test.ts:138-140` asserts
`[...PALETTE_KEYS].sort() === Object.keys(palette.dark).sort()`. So a package that creates N palette
tokens anchors N of them or reds that pin — it has no discretion. U3.1 created eight
(`successLight`, `warningLight`, `infoLight`, `warningAccent`, and the four `*OnLight`), so eight
anchors, **+16 rows, 115 → 131**.

Observed RED, verbatim, before the anchors landed:

```
FAIL  features/demo/ui/inputs/__tests__/rn-token-parity.test.ts
      > pins every palette key in BOTH scheme halves (D2, amended)
AssertionError: the guard must anchor exactly the palette tokens:
  expected [ 'background', …(31) ] to deeply equal [ 'background', …(39) ]
  -   "errorOnLight", "infoLight", "infoOnLight", "successLight",
  -   "successOnLight", "warningAccent", "warningLight", "warningOnLight",
```

`check-rn-parity.mjs`'s SCHEDULE docblock is corrected in place (it is the artefact that carried the
wrong figure) and now records the reasoning, so the next reader does not re-derive it. **Final:
40 palette keys / 131 anchor rows.** §9 clause 1's end-state arithmetic also moves — it says
"+4 status keys from U3.1, ~44 KEYS at the end". The real end state is **65 keys / 135 rows** once
U8.2 adds `gridSubtle`. Correction owed to the plan (§7).

### R-2 · A80's "no italic" is a rule about ONE COMPONENT, never about the app. The blanket sweep the row invites would drift AWAY from the phone.

A80's Demo action: *"No icon, no illustration, no glass, no border, no italic"*, plus *"The demo's
italic-13px-faint treatment is a consistent, deliberate demo idiom"*. The second clause is false and
the first is scoped narrower than it reads.

**Measured at `dd5551ec`: the phone carries 21 `fontStyle: 'italic'` sites of its own** in
non-test source. Three of them are the direct counterparts of the demo's in-card empty lines:

| Phone | Values |
|---|---|
| `src/features/case-management/components/CaseCard.tsx:274-278` | `fontSize.base` 16 · `textSecondary` · **italic** |

And `EmptyState` itself is mounted at **exactly one** site on the phone —
`case-management/components/CaseList.tsx:194` — which is why its 48pt block reads correctly there and
would be absurd inside a 40pt card row.

So the italic idiom is the **phone's**, not the demo's, and de-italicising the four in-card lines
would have been drift introduced by this package. U3.4 converts five screen-level sites and rules on
the other fifteen. The ruling is pinned (`controls/__tests__/empty-state.test.tsx`), not just written
down.

### R-3 · `map/LocationRow.tsx`'s `borderRadius: 12` is phone-exact. A57's suspicion is unfounded.

A57 flags it as *"a card-radius row — check against phone §2.C before changing"*. Checked at source:

### R-4 · D15's "92 → 64 / +108 → +80" are PHONE numbers and do not transfer. The demo's honest trim is 18px.

The phone's old block was `paddingVertical: md` (16 both edges) + `minHeight: touchTarget.large` (56)
+ `marginBottom: md` (16) — its own comment at `MainHeader.tsx:106-109` names the 92 and the +108.
**The demo has never carried the 56pt floor or the 16pt bottom margin.** Porting the recipe
(`4 / 16 / minHeight 44 / no margin`) trims the demo's header by **18px**, not 28. Reproducing 28
would mean inventing padding in order to delete it.

The pin therefore asserts **the phone's recipe**, and its docblock says why it does not assert 28.

it, no matrix row names it, and it would be an unanchorable web-side key.

The module docblock now carries **phone §1.2 note 2** as the plan's row requires, plus the pairing
contract that follows from it (fill `*Light`, 1px border `*`, text `*OnLight`; a bare dot or 1px
selection accent takes `warningAccent`/`infoDark`/`successDark`/`error` directly).

## 7. CONSUME-ME for U3.2 and U3.3 — the status keys and how to read them

**The one sentence every consumer gets wrong once (phone §1.2 note 2, now in `palette.ts`'s
docblock):** *in DARK the `*Light` names mean the DARK BACKGROUND TONE the matching `*OnLight`
foreground sits on.* They are not lighter shades. `successLight` `#0f6b42` is **darker** than
`success` `#10d177`. The names are historical — coined for the light theme, where they genuinely are
pale tints — and kept so one flat name works in both schemes.

**The pairing contract.**

| You are painting | fill | border (1px) | text / icon |
|---|---|---|---|
| A badge, chip or banner | `colors.<sev>Light` | `colors.<sev>` | `colors.<sev>OnLight` |
| A bare dot or a 1px selection accent | — | — | the ACCENT, directly |

The accents, and they are **not** the same tokens as the badge trio:

```ts
started  -> colors.warningAccent   // #ffc62b dark · #b45309 light   6.82 / 4.58
working  -> colors.infoDark        // #7a9fc4 dark · #2563eb light   3.87 / 4.72
complete -> colors.successDark     // #0faa5e dark · #059669 light   3.54 / 3.44
incident -> colors.error           // #ff4757 dark · #ef4444 light   3.21 / 3.44
```

Those four are exactly what the plan's `STATUS_ACCENT` names, and rows 22-25 + 30 in
`palette-contrast.test.ts` already pin them at the constants. **`STATUS_ACCENT` must resolve to
those tokens, not retype their hexes** — a retyped `'#ffc62b'` is indistinguishable from
`warningDark` and row 30's trap closes on it.

**Five things that will bite:**

1. **`warningAccent !== warningDark`, even though dark spells them the same hex.** Light is
   `#b45309` vs `#d97706`. They are two guard rows. Never alias one to the other.
2. **`infoLight === borderLight === '#2e5f97'` in dark.** Same value, two tokens, deliberately not
   collapsed. Spend the one that says what you mean.
3. **All four dark `*OnLight` are `#f0f4f8`, which is also `colors.text`.** Do not "simplify" them to
   `colors.text` — light's four are four different hexes and the branchless read is the point.
4. **`#f0f4f8` is NOT on the banned-literal list** (it is live in 50 files). So a stray
   `color: '#f0f4f8'` in a badge will not red; reach for `colors.<sev>OnLight` on purpose.
5. **§C.3 rule 1 still binds:** never `colors.error` as normal-size text. Severity goes on the icon
   (3:1) and the fill; text takes `*OnLight` or `colors.text`.

**Adding any new palette key anchors it.** `PALETTE_KEYS` in `check-rn-parity.mjs` is pinned by
membership against `Object.keys(palette.dark)` — there is no discretion, and the pin reds
immediately. Add the key to **both halves** or it is a compile error.

**Also relevant to U3.3's `Banner`:** its recipe (`{border '1px solid <sev>', background '<sevLight>',
message + icon '<sevOnLight>'}`) is now buildable end to end; every token it names exists. The plan's
"the fill is OPAQUE, never a glass gradient" is satisfiable — all four `*Light` values are flat
hexes with no alpha, in both halves.

**Relevant to whoever holds `ExportCaseCard.tsx` next (U2.4):** U3.4 touched only `:223`'s
empty-state block. `boxBase` at `:75` is untouched.

**Relevant to U5.2/U5.3:** `ui/controls/EmptyState.tsx` exists and takes an optional `action`
ReactNode. `LocationList` and `MapScreen`'s empty states (A80's two mis-cited entries, neither of

## 8. Two likely defects in this work

1. **`CasesScreen`'s in-card "No locations yet" is now 16px — larger than the 14px location-row names
   directly above it.** That is what phone `CaseCard.tsx:275` renders (`Typography.fontSize.base`),
   lifted per §4.1 item 7 and §4.2's no-tidying rule, so it is deliberate. But the demo's card is a
   web div stack rather than the phone's RN layout, and this is precisely the class of thing D1's
   side-by-side checkpoint exists to catch. **If it reads wrong on the device pass, the fix is to
   raise it as a phone-side finding (§8 of the plan), not to quietly re-tune the demo** — the value
   is the phone's.

2. **The keep-list census will red on any *legitimate* new italic, and the tempting fix is to edit a
   number.** Every entry carries its ruling for that reason, and the assertion message says so
   ("rule on it here, do not edit the number"). The failure mode to watch for in review: a later
   package adds a live-data italic, sees the red, and increments a count without writing why. A
   secondary risk is the comment-stripping regex — `/\/\*[\s\S]*?\*\//g` is not string-aware, so a
   `/*` inside a string literal under `ui/` would eat source. None exists today (checked); if one
   appears the census silently *under*-counts, which reds rather than passes, but the message would
   be misleading.

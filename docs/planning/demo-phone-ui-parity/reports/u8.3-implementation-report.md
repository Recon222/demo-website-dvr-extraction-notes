Icon size **24** is confirmed *by absence of a number*, which is worth stating plainly because it is
the one value in the row that is not written anywhere: all four `tabBarIcon` render props take the

### 1.2 D6 — CONFIRMED at source, and now pinned rather than merely commented

documented divergence with no guard is one refactor away from being silently "fixed".

## §2 — What shipped

```
bar fill      linear-gradient(180deg,#1e3450,#16283c)  ->  backgroundColor: colors.card   (#0e3965)
borderTop     1px solid #28456b                        ->  1px solid colors.border        (#1c4e84)
paddingTop    8                                        ->  6
active tint   #4BA3D4                                  ->  colors.primary                 (#2B8CC1)
inactive tint #5d7a9a                                  ->  colors.textSecondary           (#99badd)
icon size     25                                       ->  24   (x4 glyphs)
TAB_BAR_HEIGHT 50                                      ->  50   (D6 — unchanged, now pinned)
```

**Tokens, not literals — and two of them are compulsory.** `#0e3965` and `#1c4e84` are banned bare
under `ui/` by the A97/U0.5 guard (`ui/__tests__/glass-tokens.test.ts:315,318`, exempting only the
token modules), so a literal port would have reddened that guard. `#2B8CC1` and `#99badd` are *not*
banned (the guard's docblock explains why: their values did not move, so they carry no re-drift
risk) — they go through `colors` anyway, per the brief.

**`backgroundColor` rather than the `background` shorthand.** The flatness is then structural: a
future gradient has to delete a longhand rather than win a cascade, and the "no `backgroundImage`"
pin has something to observe. Measured, not assumed — jsdom expanded the old `background:
linear-gradient(...)` into `backgroundColor: 'transparent'` + a `backgroundImage`, which is the exact
string the RED quotes.

**The `borderTop` shorthand is kept, and that is compatible with THE LIT-EDGE RULE.** The rule
(HANDOFF.md:57) governs glass *fragments* and consumers writing over a **spread**. `TabBar`'s style
object has no spread, holds no border longhands, and imports no fragment — so there is no
paint-1-OK/paint-2-FAIL update path to trip, and the repo-wide `console.error` conflicting-property
tripwire stays silent (full suite green). Probe P5 additionally proves jsdom *does* expand
`border-top` into `borderTopColor`, so the pin reads the shipped value rather than an empty
declaration. Converting to three longhands would be a larger diff pinning the same thing.

**`aria-current="page"` kept** (the WCAG 1.4.1/4.1.2 fix). Its comment previously argued from the two
old hexes; it now argues from the mechanism, because the port swapped *which* two hues a colour-blind
visitor cannot separate — it did not remove the problem. `#2B8CC1` vs `#99badd` is still hue-only
signalling across four destinations, so the announcement is still the only non-visual cue.

## §5 — Proposed deferrals (house format — `dt-review-aggregator` decides and writes)

### Deferral 1 — the tab bar's `boxShadow` has no phone counterpart

- **Source:** U8.3 implementation, `features/demo/ui/controls/TabBar.tsx:96`.
- **What:** `boxShadow: '0 -6px 18px rgba(0,0,0,0.28)'` survives the port. The phone's `tabBarStyle`
  (`app/(tabs)/_layout.tsx:15-19`) sets no shadow key at all; `@react-navigation/bottom-tabs` supplies
  its own platform elevation, which a web `div` does not have. It is also the **only** entry in the
  demo's `BOXSHADOW` census with an upward offset (`demo-ui-inventory.md:703`, 1x).
- **Why deferred:** neither A63's phone column nor the plan §5 row names it, so removing it is a
  judgement about how the bar should *read* on a web surface with no native elevation — the exact
  class GATES §13/§14 reserve to the owner's device pass. An implementer deleting it unasked would be
  restyling past the spec on the last package of the last wave.
- **Trigger:** the **U8-exit owner device pass** (GATES §13, "final side-by-side"). If the bar reads
  as floating against the phone's flush bar, delete the key; if it reads correct, record it in A63's
  phone column as a deliberate web-only compensation for the missing native elevation. Either way the
  row closes at that checkpoint — it does not survive into a later campaign.

### Deferral 2 — the active tab is still hue-only for sighted users

- **Source:** U8.3 implementation, `features/demo/ui/controls/TabBar.tsx:119`.
- **What:** the port swapped the active/inactive pair from `#4BA3D4`/`#5d7a9a` to
  `#2B8CC1`/`#99badd`. `aria-current="page"` covers screen readers (and is pinned), but a sighted
  visitor who cannot separate those two blues still has no non-colour cue across four destinations.
  The phone has the same property and adds a **label** under each icon (`tabBarActiveTintColor`
  applies to the label too); the demo's bar renders icons only, so it has strictly less signal than
  the surface it is porting.
- **Why deferred:** adding labels changes the bar's information design and its 50px budget (D6) —
  6 + 24 + label + 12 does not fit — so it is a plan-level decision, not a token port. Out of scope
  for an S package whose row is six values.
- **Trigger:** whichever comes first — (a) the U8-exit owner device pass rules on whether the demo's
  bar should carry the phone's labels, or (b) any future package that revisits `TAB_BAR_HEIGHT`
  (D6's 50 is the binding constraint, so the height and the labels have to be decided together).

## §6 — Two likely defects (as required)

1. **The kept `boxShadow` is the most likely thing a reviewer calls wrong.** It is a real
   demo↔phone divergence that this package saw and chose not to close (§1.3, deferral 1). If the
   intended reading of "the last piece of chrome" was *all* of the bar's chrome rather than the six
   listed values, this is under-porting and the fix is a one-key delete plus a pin.
2. **The `borderTop` shorthand may be read as a LIT-EDGE RULE violation on sight.** §2 argues it is
   not (no spread, no fragment, no border longhand siblings, tripwire silent, P5 KILLED) — but the
   rule's wording names `borderTop` explicitly, and a lane reading the rule without the "after a
   spread" qualifier will flag it. Refutable in either direction cheaply; converting to
   `borderTopWidth`/`Style`/`Color` costs two lines and pins identically.

A third, smaller: the icon-size pin asserts the SVG `width`/`height` **attributes**, not a rendered
box. That is the right observable here (jsdom lays nothing out, and the attribute is what the
component writes), but it is an attribute-equality pin and P4 is what proves it falsifiable rather
than decorative.

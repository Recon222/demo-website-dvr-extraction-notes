## 1. REFUTATIONS — verified against source first, as the brief requires

Six claims in the brief, the plan, the matrix and the phone's own component did not survive contact
with the tree. Each carries `file:line`, and each one that could regress silently is **pinned**.

### R1 — `accessibilityState={{ selected }}` does not port. The web spelling is `aria-pressed`

The phone's chips carry `accessibilityState={{ selected: isActive }}`
(`MapFiltersSheet.tsx:156`, `:201`). RN maps that to `aria-selected` on the web, and
**`aria-selected` is only valid on `option` / `tab` / `row` / `gridcell` / `treeitem`** — on a
`role="button"` it is ignored by every AT. A literal port would have shipped a chip whose selected
state is announced nowhere, dressed as copy-parity.

`aria-pressed` is the two-state toggle-button semantic and is also what makes the state queryable
without reading styles. Both chip rows take it. Probe **P19** shows the pins red on its removal.

**Consequence for the testIDs.** The phone's chip testID is two-state —
`isActive ? `filter-status-${status}-active` : `filter-status-${status}`` (`:144`) — and it exists
*because* RN has no queryable state attribute to assert instead. The demo does, so the testid is
STABLE (`filter-status-${status}`) and the state lives on `aria-pressed`. A testid that moves with
state would make every query in this repo's suite state-dependent for no gain. **Deviation, named.**

### R2 — U5.2's consume-me says the wire-up is "one line". It is one line plus three handlers

`u5.2-implementation-report.md` §9: *"U5.3 — your wire-up is one line"*, then lists the rest as
notes. Measured, the screen needs **four** additions before the sheet does anything:
`onOpenFilters` (the one line), `handleStatusToggle`, `handleClearAllFilters` (which does not exist
— `handleClearFilters` is only the first half of the phone's contract, U5.2's own §9 says so), and
`setProximityRadius` reaching a caller for the first time since U5.2 deleted the preset pills. Plus
`filtersVisible`, its two callbacks, and its reset. Not a contradiction of the note's *spirit* — the
seam was genuinely clean — but "one line" would leave a sheet whose every control is inert.

### R3 — `severityTone()` takes a SEVERITY, not a status, and the wrong call is silent

`severityTone(status)` compiles nowhere (`StatusSeverity` is a closed union) but it does not
*throw*: in JS it resolves `c['completeLight']` to `undefined` and paints nothing. It is exactly the
mistake `tokens/status.ts:47-60` builds `STATUS_SEVERITY` to prevent, and it is one keystroke from
the correct call. **I made it, in the first draft of the test file**, and the pin caught it as an
empty expected-style declaration rather than a wrong colour. Recorded because the next reader of
these two lookups is one keystroke from the same place; the fix is always `STATUS_SEVERITY[status]`
between them.

### R4 — Plan §5's U5.3 row calls the toggle row "a `Toggle`". The phone's is a LABEL-LESS switch

The row and matrix A82 both say *"a `Toggle` row 'Filter by radius'"*, which reads as the demo's
`Toggle` drawing its own labelled row. It does not: the phone passes the shared `<Switch>` **no
`label` prop at all** (`MapFiltersSheet.tsx:171-179`) and draws its own 14/500 row
(`styles.switchRow` `:263-273`), because the shared control's label is 16/500 and reserves a bottom
margin (`containerStyle={{ marginBottom: 0 }}` at `:178` is the phone cancelling it).

The demo's port is `<Toggle hideLabel>` inside a hand-drawn row — and `hideLabel` is **the prop
U2.3 added for exactly this host** (`_shared.tsx:698-708`: *"Paint the track ALONE … for a host that
already draws the label itself"*). Hand-rolling a fourth track would red
`screens/__tests__/one-switch-renderer.test.ts`. The row's wording is right in outcome and wrong in
mechanism; stated here so nobody "fixes" it toward a labelled `Toggle`.

### R5 — The subtitle's plural is keyed off `locationCount` in BOTH arms, and that is not a typo

`MapFiltersSheet.tsx:94-98`: `plural` comes from `locationCount` even in the `N of M` arm, so a
narrowed single-location case reads `0 of 1 location shown` rather than `0 of 1 locations shown`.
Ported verbatim. Pinned by probe **P17**, which re-keys it to `filteredCount` and reds — otherwise
the next reader "fixes" the phone's grammar and silently diverges the copy.

### R6 — D-5's own proposed home for the live region would re-create the defect D-5 names

U5.2's deferral D-5 proposes *"the filters sheet's subtitle (`N of M locations shown`, A82)"* as the
live region's home, having just recorded that *"a live region that appears already-populated is
announced inconsistently across screen readers"*. **The shell's subtitle has precisely that shape**
— `GlassBottomSheet.tsx:376` renders it only while the sheet is mounted, already carrying its text.
Marking it `role="status"` would satisfy the letter of the deferral and reproduce its defect, on
every open.

What ships instead is the repo's own settled answer to this exact trap — `ExportModal.tsx:124-139`,
*"an `aria-live` region only announces what changes AFTER it mounts — this one mounted with its text
already in place and thereafter changed only an attribute, so a screen reader heard silence for the
whole run"* — an sr-only region written on the next tick from an empty mount, **and reset on close**
so the second open behaves like the first. See §5.

## 5. The design decision this package turns on, and what was rejected

**Problem.** U5.2 deleted the count pill that carried `role="status"` — review R-7a's *"the ONLY
feedback the filter, search and proximity controls give"* — and carried the promise forward only
onto the proximity chip. D-5 records the gap and makes U5.3's landing its trigger: *"if U5.3 lands
without deciding where the region lives, the entry is a dropped finding."*

**Chosen: an sr-only `role="status" aria-live="polite"` region inside the sheet body, mirroring the
subtitle, mounted EMPTY and written on the next tick, and RESET when the sheet closes.**

Two facts make the sheet the right owner rather than a compromise:

- **While it is open, it is the only place a filter can be changed.** The scrim covers the search
  field. So the region can never announce a change the visitor had no way to cause — which is the
  objection to a screen-level region.
- **Its subtitle already reflects all three filter states.** `locationCount` is post status/text and
  `filteredCount` is post-proximity (`MapScreen.tsx:216-217`), so a status chip moves `M` and
  proximity produces the `N of M` — every reachable change moves the string.

The empty mount + reset is not ceremony; it is the whole mechanism. `ExportModal.tsx:124-139`
records the failure it avoids in the repo's own words. Probes **P9** and **P10** red on the role and
on the reset independently.

**Rejected — `role="status"` on `GlassBottomSheet`'s subtitle.** R6: it re-creates the
already-populated defect D-5 itself names, on every open. It is also a cross-package edit to U4.1's
shell (§6.1 discipline) that would change the a11y of every future sheet for its only current
subtitle caller.

**Rejected — an always-present polite region in `MapScreen`.** It announces filter changes to a
visitor who cannot see what caused them, and invents a demo-only always-on surface with no phone
counterpart — the divergence class D-5 says should be decided once.

**Rejected — hoisting `srOnly` out of `ExportModal.tsx` to share it.** The right end state, the
wrong package: it means editing a screen no U5 row owns. A second copy ships with a comment naming
the first, and the duplication is proposed as deferral **D-1** rather than smuggled across a
boundary. (The census sees both: `ExportModal.tsx:74` and `MapFiltersSheet.tsx:209`.)

**Rejected — leaving D-5 open.** Its own trigger forbids it.

## 9. Deferral PROPOSALS (house format — the aggregator decides and writes)

**D-1 · `srOnly` is now declared twice, in two screens**
- **Source:** U5.3 implementation, §5.
- **What:** the nine-line visually-hidden style constant exists at `ExportModal.tsx:70-80` and now
  at `MapFiltersSheet.tsx:200-210`. The census sees both (`ExportModal.tsx:74` /
  `MapFiltersSheet.tsx:209` share a `margin: -1`). It is the demo's web analog of the phone's
  `AccessibilityInfo.announceForAccessibility` target and there will be a third caller the next time
  a surface needs to announce something a sighted visitor reads elsewhere.
- **Why deferred:** hoisting it means editing `screens/ExportModal.tsx`, which no U5 row owns, and
  choosing a home (`screens/_shared.tsx` is the natural one — U5.3 already imports it for `Toggle`).
  That is a shared-file write from a W3 package, i.e. the cross-lane collision §6.1 serialises
  against. A second copy with a comment naming the first is the honest interim.
- **Trigger:** **the first package that opens `ExportModal.tsx` for anything else**, or **U8.2's
  banned-literal / closing sweep over `ui/**`** if none does — the same trigger family as U5.4's
  D-1/D-2/D-3. Both sites carry the comment; if U8.2 lands without collapsing them, the entry is a
  dropped finding.

**D-2 · The demo has no light-scheme rendering of `MapFiltersSheet` to measure**
- **Source:** U5.3 implementation, row 45's second assertion.
- **What:** row 45's first assertion measures BOTH scheme halves of `textSecondary` on the `sheet`
  tier, but the second — the AT-the-constant half U0.5's rule requires — can only ever read the
  consumed scheme, because `MAP_FILTER_SECTION_LABEL.color` is `colors.textSecondary` and `colors`
  is `palette[scheme]`. Every recipe in the demo has this shape; this row is where it becomes
  visible, because it is the first contrast row whose constant lives in a component rather than in
  a token module.
- **Why deferred:** the fix is not local. It is either a scheme-parameterised recipe function
  (`sectionLabel(s: ColorScheme)`, which no consumer wants and which §9 clause 12 deliberately

## 12. Two likely defects (where I would look first)

1. **`handleClearFilters` and `handleClearAllFilters` differ by one line and sit six lines apart.**
   They are the phone's own two functions and their difference is a real product decision — the
   sheet-empty-state Clear must not turn proximity off, because that button appears in response to a
   *status/text* filter and deactivating the ring would undo something the visitor did not ask
   about. But they read like a duplication, they are named almost identically, and the "obvious
   cleanup" (`onClearFilters={handleClearAllFilters}`) type-checks, passes review at a glance, and
   is caught by exactly one test. Probes P5 and P6 red in opposite directions and are the only
   things standing between this pair and a one-line collapse. **If either handler is touched, run
   both.**
2. **The live region and the visible subtitle carry the same string from two different
   expressions.** The subtitle is computed in `MapFiltersSheet` and passed to the shell; the
   announcement is `useState` + `useEffect` over the same local. Nothing forces them to agree — a
   future edit that formats the subtitle at the call site (say, appending a proximity radius) would
   leave the region announcing the old shape, silently, because `getAllByText` in the subtitle pins
   would then find one node each and those pins assert **2**. That is a real tripwire, and it is
   also the tripwire's weak point: a reader who sees `toHaveLength(2)` fail may "fix" it to `1`
   rather than re-point the region. If the subtitle's construction moves, move the announcement with
   it and keep the pairing assertion.

Second-order, worth one sentence: **the sheet's proximity switch and the map's proximity chip ✕
share the accessible name "Deactivate proximity mode"** while both are in the DOM. It is not a
defect — `aria-modal="true"` removes the chip from the AT's view whenever the sheet is open, so the
two names are never live together — but `getByLabelText('Deactivate proximity mode')` in a future
test will find both, and the pins here deliberately use testids for that reason.

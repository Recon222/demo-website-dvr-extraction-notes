### The exported shape

```ts
// features/demo/ui/tokens/glass-tiers.ts
export type GlassVariant = 'card' | 'nestedCard' | 'elevated' | 'header' | 'sheet' | 'recessed'
export type GlassTier = {
  readonly gradient: readonly [string, string]
  readonly border: string
  readonly highlightTop: string
  readonly innerShadow: string
}
export const GLASS_TIER = { light: { …six… }, dark: { …six… } }
  as const satisfies Record<ColorScheme, Record<GlassVariant, GlassTier>>
```

`satisfies` and not an annotation: `as const` keeps every value's literal type for consumers, and the
constraint still makes *a tier missing from one half* or *a tier missing one of its four parts* a
compile error in both directions — the same device `tokens/palette.ts:166` uses.

### Design decisions, each with the alternative rejected

1. **One nested literal, mirroring `GlassColors`' own nesting** — not `palette.ts`'s two module-level
   consts. *Rejected:* the palette shape. The guard addresses the RN side with a three-level scope
   (`['export const GlassColors','dark: {','card: {']`); mirroring it means **one scope shape serves
   both sides** (`rnTierScope` / `webTierScope`, identical bodies) instead of a second,
   differently-shaped web reader to keep in step. Nothing is given up: the compile-time key-set check
   comes from `satisfies` on the same literal.
2. **Unspaced `rgba()`**, against the phone's spelling. *Rejected:* copying the phone's spacing —
   `glass-tokens.test.ts` pins the composed gradients byte-exactly, so it would redden shape pins for
   a formatting change. `norm()` (`check-rn-parity.mjs:63`) exists to reconcile the two and is applied
   to both sides.
3. **`import type { ColorScheme }` is the module's only import.** *Rejected:* spelling `'light' |
   'dark'` inline — duplicates a name one file over. Type imports are erased, so the runtime-cycle
   hazard (`glass-tokens.ts` → here, never the reverse) is untouched; a cycle would evaluate the
   template literals against `undefined` and ship `linear-gradient(180deg,undefined,undefined)` past
   every type check.
4. **Plain template literals under `as const`, not getters.** In-tree precedent (`gradientAccent`
   always was one; U0.1 made `border`/`borderBtn` two more) and measured safe: no `...GLASS` spread,
   no `Object.keys/values/entries(GLASS)`, no `keyof typeof GLASS`, no concatenation of the derived
   keys across the 54 importers. *Rejected:* getters — nothing needs laziness and they break `toEqual`.
5. **Both gradient stops are separate anchor KEYS.** *Rejected:* one key per gradient. An anchor row
   is the unit of `PARSE-FAILED` isolation, so a gradient whose second stop moves must fail without
   taking the first stop's verdict with it.
6. **Twelve `BANNED` entries — the dark gradient stops only.** *Rejected:* all 24 dark parts (or all
   48). The `BANNED` docblock's own rule is *"EVERY ENTRY IS A CURRENT LIVE VALUE"* of a live token,
   and its schedule names *"U1.1's tier **stops**"*. The `border` and `highlightTop` values become
   re-inlinable CSS only when U1.2/U1.3/U1.4/U2.4/U4.1 wire them into a `border`/`borderTopColor`
   recipe; the five `innerShadow` blacks (`rgba(0,0,0,0.2)` … `0.45`) are indistinguishable from
   ordinary drop shadows and banning them would misfile a future generic shadow as tier re-drift —
   the same reason the plan leaves `innerShadow` out of the anchor set. Also rejected on measurement
   grounds *against* my first instinct: all 24 dark values have **zero** occurrences under `ui/`, so
   "it costs no sweep" is true of every one of them and is therefore not a reason to ban any.
   Bare-stop bans do earn their place: five call sites re-derive the OLD card stops at other alphas
   today (A33) and the composed-string bans sail straight over every one.

### The two SURVIVED results, and what I did about them

**P4b / P4b′ — severing a derivation back to its own literal is invisible.** Replacing
`` `linear-gradient(180deg,${tier.card.gradient[0]},${tier.card.gradient[1]})` `` with the identical

and `/demo` renders the old gradient.

which fails in that second step. It is *not* a tautology — its right-hand side is composed from a
different module. Stated honestly in its own comment: **no single mutation demonstrates the two-step
failure**; what P4c/P4d/P4e demonstrate is that the pin reads the relationship rather than restating
the literal. It also pins the `borderAccent` **negative**, so U1.3 is forced to complete the
derivation when it lands `0.25`.

**P2/P2b — a pin I wrote and then deleted.** The runtime tier-shape case died to the same mutation as

### D-1 — `flattenOver`'s per-fold rounding diverges from the phone's float compositing by up to 0.32 ΔE

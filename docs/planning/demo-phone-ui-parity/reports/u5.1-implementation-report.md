## 1. REFUTATIONS — verified against source, first, as the brief requires

Six claims in the plan, the matrix and the brief did not survive contact with the phone or with
the tree. Each is refuted with `file:line` and each refutation is **pinned**, so a later "fix"
back toward the doc must red rather than pass quietly.

### R1 — The map sheet ground is NOT the `sheet` glass tier (plan §5 U5.1 row; matrix A84)

Both say `background → sheet` gradient (A38). The phone says the opposite, **in source, twice**,
and it is a performance ruling rather than a preference:

> `map-view/constants/index.ts:339-343` — *"Fully opaque (alpha 1.0) on purpose, in BOTH themes:
> the sheet translates over the live Mapbox GL surface, and a translucent surface forces the
> compositor to keep rendering the map behind the sheet AND alpha-blend it on every drag frame
> (a UI-thread cost that dropped the drag to ~45fps). At 0.97-0.99 the translucency was visually
> imperceptible but not free; opaque lets the compositor occlude the map region behind the sheet.
> **This is why the sheet does NOT use `GlassColors[scheme].sheet`, whose dark gradient starts at
> 0.98 alpha.**"*

`map-view/README.md:407` restates it as the opaque-sheet performance rule, and
`phone-ui-delta-inventory.md:5433` already quoted that line — the plan row simply did not act on
it. The shipped value is `SHEET_SURFACE_COLORS[scheme].backgroundGradient` =
`[background, backgroundSecondary, background]` at `locations [0, 0.5, 1]`, vertical
(`constants/index.ts:350-367`, painted by `SheetBackground.tsx:31-41`).

**Ported as the phone ships it.** The demo's `MapBottomSheet` drags over a live `mapbox-gl`
canvas, so the reasoning transfers unchanged. Pinned two ways: a token pin asserting the composed
three-stop value, and `expect(...).not.toContain(GLASS_TIER[scheme].sheet.gradient[0])` so the
A84 reading cannot be reinstated silently.

### R2 — Map sheet ROWS are the `card` tier, not `nestedCard` (matrix A84)

A84: *"`rowBg`/`rowBorder` → `nestedCard` (A33/A34)"*. The phone's `LocationRow.tsx:70` reads
`GlassColors[colorScheme].card`; its docblock at `:5` says *"Renders as a glass card:
`GlassColors[scheme].card` gradient"*; the shell paints `glass.gradient` at `:88` and
`glass.border` at `:91`. **Matrix row 18 agrees with the phone against A84** — *"Phone rebuilt it
on `GlassColors[scheme].card` + `Layout.shadow.card`"*. The nested tier is
`LocationDetailCard`'s four info cards (`<Card glass glassVariant="nestedCard">`), which is
`infoBg`. Ported that way, and `rowBg !== infoBg` is pinned so the two tiers cannot collapse.

Note this also **reconciles** the plan row's own `border/divider/rowBorder → #1c4e84 family`
clause, which is correct for `rowBorder` only under the `card` reading (`card.border` is
`rgba(28,78,132,0.5)`, i.e. `#1c4e84` at 50%). Under A84's `nestedCard` reading it would have
been `rgba(43,140,193,0.45)` — a different family. The plan text and the phone agree; A84 is the
outlier.

## 5. Deviations, with justification

1. **`MAP_GLASS_COLORS` ships two halves** where A84 ratified dark-only. D2's amended text is
   later and binds harder; the light containerBg's alpha move was the redesign trigger; the drift
   guard now pins both. `MAP_SURFACE_COLORS` / `CLUSTER_COLORS` / `CAMERA_MARKER` stay
   single-valued for the phone's own stated reason.
2. **`MapCanvas`'s retry button changes colour** — one line beyond the row's file list.
   `SHEET_COLORS.accent`'s only reader is a **filled control**, so A19's binding rider governs its
   pair; label `#f0f4f8` on `#1a8fc2` measured ≈3.2:1, under the 4.5 text floor. It is now
   `colors.onPrimary` on `primaryDark` (5.80:1, A19's own figure). **Matrix A19 says the rider
   "bites in this port at exactly one place (the map filter-count badge)" — this is a second.**
   The neighbouring bare `#f0f4f8` on the error overlay becomes `colors.text` in the same block
   (no value change).
3. **The map-domain values are SPELLED, not derived.** The drift guard reads source text, so
   `withAlpha(colors.background, 0.82)` would become a `PARSE-FAILED` row rather than an anchor.
   Same split `tokens/glass-tiers.ts` uses for its 48; the derivations are pinned in the test
   instead, so a palette re-tint that fails to reach the map still reds.
4. **`SHEET_COLORS.background` renamed to `backgroundGradient`** — it is no longer a colour, and
   `backgroundGradient` is the phone's own name for it. One consumer.
5. **`CLUSTER_COLORS.circle` and `CAMERA_MARKER.baseBorder` are spelled, deliberately un-aliased.**
   They are marks on satellite tiles and must NOT move when `scheme` flips; reaching for
   `palette.dark` would name a scheme half in a value position and red the r2-F24 scan. The
   `palette.dark` derivation is pinned in the test, where naming a half is allowed.
6. **The retired-ramp ban is file-scoped, not repo-wide** (R6) — the repo-wide form would redden
   ~15 files owned by U6/U7/U8. Deferred with a trigger.

## 11. Two likely defects (where I would look first)

1. **`SHEET_COLORS.backgroundGradient` is a `background` shorthand now, and `MapBottomSheet` is
   the only consumer that knows it.** Any later code that sets `backgroundColor` on that element —
   or spreads the sheet style and then writes `background: …` after it — silently replaces the
   gradient with a flat colour, and **jsdom accepts both**, so only the one DOM pin I added would
   catch it. This is the `background`-shorthand cousin of the lit-edge rule and it is not covered
   by the repo-wide tripwire, which watches `border`/`borderColor` only. U5.3 mounts a second
   sheet into the same screen; that is the first real chance to hit it.
2. **The map's light half is now shipped but nothing renders it, and the two "light" values have
   different provenance.** `containerBg.light` derives from `palette.light.background`;
   `border.light` is a transcribed slate with **no light-palette owner** — it merely *coincides*
   with `GLASS_TIER.light.elevated.border`. At §9 clause 12's scheme flip, a reviewer will very
   plausibly "tidy" that into an alias of the tier and quietly couple two values the phone declares
   independently, at which point a phone-side tier re-tint moves the map chrome. The docblock says
   not to; a docblock is not a gate. A second-order version of the same risk: `MAP_PIN_COLORS`,
   `CLUSTER_COLORS.circle` and `CAMERA_MARKER.baseBorder` must **not** follow that flip, and the
   only thing stopping someone re-pointing them at `colors.*` is a comment and one test.

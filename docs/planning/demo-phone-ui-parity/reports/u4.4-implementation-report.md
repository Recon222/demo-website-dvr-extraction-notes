### R-4. Rows 38–40 cannot be un-todo'd: `PdfPreview` has no loading state.

A90: *"The demo's analogs are `MediaLibrarySheet.tsx:336-404` (the fullscreen close chip) and
**`PdfPreview`'s loading state**."* The second does not exist.

`ui/chrome/PdfPreview.tsx` is **176 lines with exactly one `useState`** — `printNotice`, for a
blocked print dialog (`:27`). No spinner, no `onLoad`, no loading plate: it renders the document

The demo paints its own surround (`PdfPreview.tsx:151`, `#3a3f47`) into an iframe it controls; there
is no native viewer to match, so porting `#525659` would cargo-cult a platform constant into a place
where no platform paints it. The todo now carries that reasoning **in file**, with its un-defer
trigger.

### R-5. The lit-edge ruling is right and my U4.1 refutation was half wrong.

`reports/partner-lit-edge-ruling.md` §2: my Claim B held for **paint 1 only**. Reproduced here
independently before changing anything — jsdom, three paints, toggling the tint itself:

| form | p1 | p2 | p3 |
|---|---|---|---|
| `{ ...B_sheet, borderColor: X }` (what U4.1 shipped) | `rgb(200,200,200)` | **`rgb(2,2,2)`** | `rgb(1,1,1)` |
| `{ ...A2_longhands, borderColor: X }` (ruled) | `rgb(1,1,1)` | `rgb(2,2,2)` | `rgb(1,1,1)` |
| `{ ...A2_longhands, three side longhands }` | `rgb(200,200,200)` | `rgb(200,200,200)` | `rgb(200,200,200)` |

React writes only the style keys whose **value changed** (`setValueForStyles`), so on an update the
changed four-side shorthand is written and the unchanged `borderTopColor` is skipped. **`borderColor`
IS a four-side shorthand** — that is the half I missed, and the mirror of the half the W1 seat missed.
The ruling's sharper point is the one I had backwards: a form that survives paint 1 and fails paint 2
is *worse* than one that fails immediately, because it passes review. And my "across an UPDATE" case
toggled `opacity`, not the tint, which is precisely why my suite never exercised the failing cell —
the trap this whole campaign exists to catch, in my own test file.

Applied as ruled (option 2), in `fix(u4.1): …` on this branch.

### The border rule, now ruled (`fix(u4.1)`)

```ts
import { sheetSurface } from '@/features/demo/ui/controls/sheet-chrome'

<div style={{ ...sheetSurface, borderRightColor: X, borderBottomColor: X, borderLeftColor: X }} />
```

- **`sheetSurface` carries no shorthand key at all** — no `border`, no `borderTop`, and **no
  `borderColor`** (which is itself a four-side shorthand). Only `borderStyle`, `borderWidth: 1`,
  `borderTopWidth: 2` and the four colour longhands.
- **After spreading it, write only COLOUR LONGHANDS.** `borderRightColor` / `borderBottomColor` /
  `borderLeftColor`, plus `borderTopColor` only if you really mean to recolour the lit edge.
- **Why, in one line:** React writes only the keys whose value changed, so any shorthand slot in the
  fragment keeps the edge on paint 1 and loses it on paint 2 — silently, with a `conflicting
  property` warning nobody reads. My U4.1 consume-me said `borderColor` was survivable. **It is not.
  That line is superseded by this one.**
- One benign asymmetry worth knowing: a consumer that applies those longhands **conditionally** and
  then drops them gets `sheetSurface`'s own tint back, not `currentColor`, because the tint lives in
  longhands here too. Every shorthand-carrying form loses the sides in that cell.
- **Assert per side, never through the shorthand.** Raised by U3.3 mid-package and verified here:
  jsdom does **not** synthesize `border-color` back from four longhands, so
  `el.style.borderColor` reads `''` over this fragment. A pin written against the shorthand asserts
  over an empty declaration and stays green after the tint is deleted — plan §4.2's trap, arriving
  by a new route. `sheet-chrome.test.tsx` now carries a `sides(el)` helper returning
  `{ top, right, bottom, left }` and pins `el.style.borderColor === ''` explicitly so the next
  reader does not rediscover it. Every U4.4 pin already read per-side; copy the helper rather than
  the shorthand.

## 9. Deferral PROPOSALS

**1. Contrast rows 38–40 have no surface to measure.**
- **Source:** matrix A90, contrast rows 38–40; `ui/chrome/PdfPreview.tsx` read in full.
- **What:** A90 names *"`PdfPreview`'s loading state"* as the demo's analog of the phone's PDF
  loading plate. There is none — 176 lines, one `useState` (`printNotice`), no spinner, no `onLoad`,
  `srcDoc` straight into an iframe. So `PDF_LOADING_SCRIM` has nothing to ground and
  `PDF_VIEWER_CHROME` would port a platform fact (`#525659`, Chrome's own viewer grey) into a
  surround the demo paints itself (`#3a3f47`).
- **Why deferred:** Building a loading overlay to satisfy a contrast row is building UI to make a
  test pass. DEF-UI-005 is "the loading MESSAGE is invisible"; the demo displays no message, so it
  does not have the defect.
- **Trigger:** the day `PdfPreview` grows a real loading affordance — most plausibly if the iframe
  ever becomes async or the preview moves to `pdfjs` rendering. Whoever adds it lands
  `PDF_LOADING_SCRIM = 'rgba(0, 40, 83, 0.9)'` + `PDF_VIEWER_CHROME` and un-todos rows 38–40 in the
  same PR. The todo in `palette-contrast.test.ts` carries this text.

**2. `rgba(4,8,14,*)` cannot be banned until U4.2, U4.3 and U8.1 have run.**
- **Source:** U4.4; the survivor table in §3.
- **What:** The natural end-state guard is a `RETIRED`-style entry in `tokens/__tests__/palette.test.ts`
  forbidding `rgba(4,8,14,*)` anywhere under `ui/` — the same mechanism that already keeps the
  retired navy ramp out. It cannot land yet: five modal scrims are U4.2's/U4.3's, `ExitDialog`'s
  `0.72` is a **permanent** D12 exemption, and `BootSequence`'s is a button fill U8.1 owns.
- **Why deferred:** Adding it now reddens five files this package must not touch, and the ban needs
  a documented exemption for `ExitDialog` that only makes sense once the sweep is otherwise complete.
- **Trigger:** the U4 phase merge (after U4.2 and U4.3 land) for the `0.55`/`0.66` half — at which
  point only `ExitDialog` and `BootSequence` remain and the entry can ship with those two named as
  exemptions. §9 clause 7's census (*"one scrim (plus two named exceptions)"*) is the acceptance
  criterion, and those are exactly the two.

**3. A React `conflicting property` tripwire is not installed.**
- **Source:** `partner-lit-edge-ruling.md` §4 item 3(a) — recommended, not ruled.
- **What:** React's own dev warning fired in **100%** of the measured update-clobber cells and in no
  correct cell. Failing any test on a `console.error` matching `/conflicting property/` in
  `vitest.setup.ts` would catch this bug class everywhere a test re-renders, for about four lines.
- **Why deferred:** `vitest.setup.ts` is shared by all 274 test files and every concurrent lane. A
  global console tripwire flipped mid-wave can redden another package's in-flight work for a reason
  that has nothing to do with it, and neither U4.4's row nor the ruling assigns it an owner.
- **Trigger:** the U4 phase merge, or U8 (which already owns the shared harness). The static half of
  the ruling's 3(b) — no `border` / `borderColor` / `borderTop` key in any object literal that
  spreads a fragment — belongs with whoever owns `glass-tokens.test.ts`'s scan, i.e. **W1's seat**.

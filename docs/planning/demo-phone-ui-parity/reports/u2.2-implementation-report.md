### R7. §4.3's `borderColor` escape hatch is worse than "wrong" — it does not survive a spread

The brief flags §4.3's bullet as wrong because `border-color` is itself a four-side shorthand. True, and the
deeper problem is the *remedy* `glass-tokens.ts:129-130` publishes: *"A consumer that must re-tint the sides
sets `borderColor` and then re-sets `borderTopColor`."* **Through a spread that does not work**, because object
spread keeps a re-assigned key at its **original insertion position**:

```
{ ...frag, borderColor: X, borderTopColor: frag.borderTopColor }
   -> key order is  borderTopColor (from the spread), borderColor, …
   -> the shorthand still lands last and still erases the lit edge
```

Proved by probe **P2b** (§3): the documented hatch, applied verbatim, reds the rendered pin with
`expected 'transparent' to be 'rgba(255, 255, 255, 0.14)'`. **`buttonStyle` therefore emits `borderStyle` +
`borderWidth` + the four `border*Color` longhands and NO shorthand at all** — the trap is removed, not
documented. Both live instances §4.3 names are gone with it: `RowActions.tsx:108` deleted (it only re-asserted
the border the fragment already carried) and `AlertDialog.tsx:182` rewritten as longhands with its value
unchanged.

### The seam

`features/demo/ui/controls/button-recipe.ts` — **`SEAM(U2.2)`**:

```ts
export const PrimaryButtonGradient = { light: ['#2563eb', '#1d3584'], dark: [GLASS.accentFrom, GLASS.accentTo] }
export const ElevatedEdges = { light: {top,bottom}, dark: {top,bottom} }   // Colors.ts:487-490, spacing verbatim
export const DangerFill    = { light: palette.light.errorDark, dark: palette.dark.errorLight }
export const SAMPLE_TINT   = withAlpha(colors.primary, 0.14)               // demo-only, D12
export type  ButtonVariant = 'primary' | 'secondary' | 'outline' | 'ghost' | 'danger'
export type  ButtonSize    = 'small' | 'medium' | 'large'
export function buttonStyle(opts?: { variant?; size?; disabled? }): CSSProperties
```

**A function, not a spreadable const** — 5 × 3 × 2 = thirty style objects, and a static fragment cannot carry
the disabled precedence, which is why all ~45 sites re-derived it by hand. Same shape and same reasoning as
U2.1's `fieldInputStyle`. **Rejected: a `<Button>` component** — that is a composition change, and D20's
behaviour carve-out names six packages; U2.2 is not one. A union-typed function makes the same invalid states
unrepresentable without changing what any surface renders.

`PrimaryButtonGradient.dark` **points at** `glass-tokens.ts`'s `ACCENT_FROM`/`ACCENT_TO` rather than restating
them: `check-rn-parity.mjs:459-460` reads those two with `readConst`, which matches **literals and not
identifier references**, so the literal has to stay there. Moving it would blind anchors 7 and 8 silently.

### Invalid states, enumerated (the brief's explicit ask)

The state space is `variant × size × disabled × scheme` = 60 cells. **All 60 are valid and reachable** — what
was representable-and-wrong *before* the seam is what the seam removes:

| Was representable | Now |
|---|---|
| A disabled primary painting the **live gradient** at `opacity: 0.45` — the demo's idiom at ~10 sites, and not a thing the phone can render (`Button.tsx:279`: the gradient renders only `&& !isDisabled`) | **Unrepresentable.** `buttonStyle({ disabled: true })` returns the flat `colors.disabled` fill with no gradient, no drop shadow, no text shadow. Probe P3. |
| A variant or size outside the five/three | **Unrepresentable** — string-literal unions. |
| Asking for the wrong **scheme** | **Unrepresentable by omission.** There is no scheme parameter; the recipe resolves `scheme` from `palette.ts`, the one consumption site §9 clause 12 protects. The three constants ship both halves so the light flip and the contrast test have them. |
| A `border` / `borderColor` shorthand erasing the lit edge from inside the recipe | **Unrepresentable** — the recipe emits no shorthand. From *outside* it is still possible, and is **pinned** three ways (§3, probes P1/P2/P2b). |
| Disabled applied uniformly across variants | **Pinned, not typed** — the phone's arms are not uniform (below), so this is a values question, and three separate tests assert it. |

**The disabled half is per-variant and this is the thing D10's plain text hides.** `Button.tsx`:
`primary` (`:116-117`), `secondary` (`:143-144`) and `danger` (`:159-160`) take `colors.disabled` as fill and
border; **`outline` (`:147`, `:152`) keeps `backgroundColor: 'transparent'` and swaps only its BORDER**;
**`ghost` (`:155-156`) has no disabled branch in its style at all.** The **label** is uniform —
`colors.disabledText` on all five (`:200, :216, :228, :231, :234`). A reading of D10 as "swap every disabled
variant to the fill" contradicts the source at two of five arms.

`disabledText` on `disabled` is below AA and **stays that way**: WCAG 1.4.3 exempts inactive controls, the
phone declines to chase those branches in as many words (`Button.tsx:225-226`), and A66 carves them out
explicitly. Inherited, not "fixed" — that is also the correct reading of A19's rider, which bites on *active*
fills.

### Not ported from `Button.tsx`, each with its reason (in the module docblock)

- **`overflow: 'hidden'`** (`:118`) — RN needs it to clip an absolutely-positioned `<LinearGradient>` **child**.
  On the web the gradient *is* the background; there is nothing to clip.
- **The 500 ms delayed spinner + the `opacity: 0`-held label** (`:64-77`, `:287-296`) — component-local state
  and a timer, i.e. behaviour. §2 puts behaviour out of scope, D20's carve-out names six packages and U2.2 is
  not one, and **no demo button has a `loading` prop**, so there is no consumer either. Deferral **§D1** below.
- **`safeImpactAsync()` / `activeOpacity`** (`:265`, `:270`) — haptics and RN press feedback, both on §2's
  phone-only-mechanics list.
- **`accessibilityRole` / `accessibilityState`** (`:276-277`) — a native `<button>` carries the role, and the
  demo's house rule is `aria-disabled` over `disabled` so keyboard focus is never stranded. Call sites keep
  owning that; a style recipe must not.

## 6. Deviations and deliberate choices — do not re-flag

1. **`glassBtnPrimary` / `glassBtnSecondary` deleted, not aliased.** An alias would carry the recipe's padding
   and min-height into every un-migrated site (a spread beats a `padding:` written before it) while leaving
   that site's `fontSize:` — written *after* the spread at ~40 sites — at the old 13/14/15. Half-ported is
   worse than either end, and §9 clause 7 wants one recipe, not two spellings of one.
2. **`ElevatedEdges` shipped with the phone's `rgba()` spacing** (R9).
3. **`AlertDialog`'s destructive arm keeps its value** (`#ff6b7a` label, `rgba(255,71,87,0.3)` edges), now as

## 8. Two likely defects in this package

**1. `medium`'s `16px 24px` padding will wrap labels in the 378 px frame that used to fit on one line.**
The phone's default size is `medium` and the demo's frame is 378 px wide, not 390–430 pt. On a two-up row each
button is ~169 px, and 48 px of horizontal padding leaves ~121 px for the label. `"Use Current Time"` at 16 px
semibold is about 130 px. **jsdom renders no layout**, so no test in this repo can see it, and `minHeight: 48`
means a wrapped label grows the button rather than clipping. The phone wraps here too at 390 pt, so this may be
correct parity rather than a defect — but it is the first thing to look at in the Playwright captures and at
the owner's device pass. Candidate surfaces: `TimeOffsetScreen` ("Use Current Time" / "Calculate"),
`CompletionScreen:137` ("Preview Time-Offset Calibration"), `CaseActionsSheet`'s 2-up grid,
`PickerStage:282/293`.

**2. The disabled repaint is the largest change with the least coverage, and on `outline`/`ghost` it may read
as *less* disabled than before.** Ten-odd sites drop `opacity: 0.45/0.5/0.55/0.6` for `colors.disabled` +
`disabledText`. On `primary`/`secondary`/`danger` that is a clear flat fill. On **`outline`** the fill stays
transparent and only the 1 px border changes `#b8d4f0 → #2e5f97`; on **`ghost`** only the label moves. That is
byte-exact to the phone (`Button.tsx:147/152/155-156`), but the demo previously faded the whole control, so a
disabled outline button is now a *subtler* signal than it was. Two of those sites have any test at all
(`OcrCaptureScreen:598` and `CompletionScreen:147`, neither asserting style). If the owner's pass reads it as a
regression, the fix is a demo-recorded divergence, not a recipe change.

**`buttonStyle(opts?)` → `CSSProperties`.** Defaults `{ variant: 'primary', size: 'medium', disabled: false }`,
matching `Button.tsx:41-43`. It resolves `scheme` itself — **do not pass one and do not reach for
`palette.dark`**; that is §9 clause 12's single-site rule.

**The five rules that matter to you:**

1. **SPREAD IT LAST.** `{ flex: 1, marginBottom: 10, ...buttonStyle({ variant: 'outline' }) }`. It owns
   `display / alignItems / justifyContent / textAlign / borderRadius / borderStyle / borderWidth / the four
   border*Color / padding / minHeight / fontSize / fontWeight / background / color / cursor` and, on
   non-disabled primary, `boxShadow` + `textShadow`. Anything it does not own (`flex`, `width`, `gap`,
   `margin*`, `flexBasis`, `opacity`, `marginTop:'auto'`) survives from before the spread.
2. **NEVER write `border:` or `borderColor:` after the spread.** Both are four-side shorthands and both erase
   the lit edge. The "re-set the longhand after" hatch `glass-tokens.ts` publishes **does not work through a
   spread** (R7, probe P2b). To re-tint a side, set that side's longhand — which now works, because the recipe
   leaves no shorthand to lose to. `AlertDialog.tsx`'s `destructiveTint` is the worked example.
3. **Picker footers → this recipe** (your row says so). `inputs/TimeField.tsx`'s `ghostBtn`/`primaryBtn` and

   the call site, port that; where they do not, they are `medium`. **Do not re-hand-roll a footer button.**
4. **`SAMPLE_TINT` is the demo-only 14 % `primary` wash**, used as `{ ...buttonStyle({ variant: 'outline' }),
   background: SAMPLE_TINT }` at three sample/fallback sites. If your radio/checkbox work meets a

## 4. Decisions and justified deviations

**4.1 · THE BANNER RULING (D19's hand-back — a ruling to propose, per the brief).**

`_pane-chrome.tsx:74-79` at `7bcb553` declined the `Banner` COMPONENT because adopting it would
move padding 13→12 and radius 10→8. **That reasoning is backwards** — moving the geometry to the
phone's numbers is the job, not the obstacle — so I took every visible part of the phone's
settings note and left the component. Both options, measured:

| | **Adopt `<Banner>`** | **Adopt the RECIPE (chosen)** |
|---|---|---|
| Geometry parity | full | full — identical, and pinned equal by a drift guard |
| Glyph | Banner's | Banner's, imported (`BannerIcon`) |
| `aria-describedby` targets (R-6) | **BROKEN** — `Banner` has no `id`; three inert controls (`AppearancePane`'s Dark Mode, `CloudSyncPane`'s switch, `ExportSecurityPane`'s Set Default Password) point at their note and `panes.test.tsx:83-102` resolves all three | kept |
| Static notes (six) | become `role="alert"` live regions announcing on mount | stay inert — R-34's finding, *"a static live region announces nothing and costs a needless AT boundary"* |
| Reactive notes (two) | `role="status"` (polite) → `role="alert"` (assertive) — a warning interrupts the picker that produced it; `panes.test.tsx:178` reds | stay polite |
| Copy | the `"Warning: "` / `"Note: "` prefixes become redundant (Banner's `aria-label` prepends the severity) and read as `"warning: Warning: …"` | prefixes keep carrying the severity to AT |
| Scope | three accessibility-tree BEHAVIOUR changes | style only |

**The deciding fact is scope, not taste.** Plan §2's D20 carve-out names the six packages allowed
a behaviour change — U2.3, U4.2, U4.3, U5.2, U5.3, U6.3. **U6.2 is not among them**, and §2's
instruction for that case is explicit: *"If a package needs one of THOSE, it is mis-scoped — stop
and raise it."* U3.3's own consume-me offers `PaneNote`-wraps-`Banner` as the alternative; that is
worse than either end, because it nests a `role="alert"` inside a `role="status"`.

So `PaneNote` now renders `Banner.tsx:114-144`'s recipe key for key — row / flex-start /
`gap: spacing.sm` / `radius.md` / `borderWidth 1` / `padding: spacing.base` / `marginTop:
spacing.xs` (the phone's `styles.note`, the only thing every settings caller passes) plus
`messageStyle` (flex 1 / 14 / `'21px'`) and the 20px severity glyph. `Banner.tsx` gains one
export, `BannerIcon` — a pure extraction, `Banner`'s own DOM is byte-identical — so the two cannot
draw different icons. **`pane-chrome.test.tsx`'s drift guard renders a `<Banner style={{marginTop:
spacing.xs}}>` and a `<PaneNote>` and asserts their declared styles are EQUAL, key for key, on
both the box and the message.** Probes P3 and P4 prove it fires on a mutation to *either* side.

`banner.test.tsx`'s adoption map is refined rather than fudged: its predicate was "imports the
module", which is no longer the same fact as "adopted the component". It now tests that
`<Banner …>` RENDERS, and a new `RECIPE_ONLY` block holds `_pane-chrome` to both halves of this
ruling — it must still import the module (or the glyphs can fork) and must still not render the
component.

**4.2 · The slider's third tint is unportable, and is recorded rather than faked.** `accentColor`
carries the phone's `minimumTrackTintColor` + `thumbTintColor` exactly (filled track and thumb).
`maximumTrackTintColor: colors.border` needs `::-webkit-slider-runnable-track` /
`::-moz-range-track` — a stylesheet. `features/demo/**` styles with `CSSProperties`, `ui/demo.css`
is frozen (§4.2 / D9), and a value moved into a class un-pins its own test. Hand-rolling the track
would trade one unportable value for a whole control the phone does not have. The demo keeps the
UA's neutral trough; the reason is at the site.

**4.3 · The pressed wash needed component-local state, and D20 permits it.** A78's `pressed wash
link@0.06` is named by the U6.2 row itself, which is D20's condition (*"component-local UI state
… where a NAMED package specifies it"*). `Pressable` gives the phone the flag; `:active` would
need a stylesheet the demo forbids, and React state is also the only form a test can read.
Released on `pointerup`, `pointerleave` **and** `pointercancel` — a press dragged off the row, or
interrupted by a scroll gesture taking the pointer, otherwise leaves the wash painted (probe Q7).

**4.4 · Deferral §23 (drawer completion dots, colour-only) is RE-RAISED UNCHANGED**, as the row
instructs. Its premise still holds at `WizardDrawer.tsx:97-99` (filled green vs filled amber, no
non-colour distinction) and its SR half is still satisfied (`:76-79` — status is in the item
button's `aria-label`, dots are `aria-hidden`). Its trigger — *"if a strict-a11y bar applies or
before any production use"* — has **not** fired: this port is a restyle, not a production launch.
Nothing changed; the owner ruled once already.

**4.5 · Two things NOT ported from the nav bar, both deliberate.** `numberOfLines={1}` on the
detail title: the catalog is closed at ten rows and its longest title ("Export Security") renders
~135px at 18/600 in a 378px bar, so the ellipsis trio would guard a case the id space cannot
produce — and it would need a `minWidth: 0` to function at all. `pressed: { opacity: 0.6 }`: the
demo has **no** pressed treatment on any button (`controls/button-recipe.ts` has none), so adding
one to two buttons here would be the per-file drift this campaign deletes. Deferral proposal 2.

## 6. Deferral proposals (the aggregator decides and writes the ledger row)

**Proposal 1 — `PaneNote` renders `Banner`'s recipe instead of `<Banner>`**
- **Source:** `features/demo/ui/screens/settings/panes/_pane-chrome.tsx` (`PaneNote`);
  `features/demo/ui/controls/__tests__/banner.test.tsx` (`RECIPE_ONLY`); D19's hand-back.
- **What:** the eight settings notes paint the phone's `Banner` recipe byte for byte and are
  pinned equal to it, but do not import the component. `<Banner>` is hard-wired to `role="alert"`
  with an explicit `aria-live` and has no `id` prop, so adopting it would break three
  `aria-describedby` targets (R-6), make six static notes announce on mount (R-34), and turn two
  polite `role="status"` notes assertive. §4.1 measures both options.
- **Why deferred:** all three are accessibility-tree BEHAVIOUR changes, and plan §2's D20
  carve-out names six packages — U2.3, U4.2, U4.3, U5.2, U5.3, U6.3 — of which U6.2 is not one.
  §2's instruction for a package that needs one is to raise it, not take it. The duplication costs
  nothing today because the drift guard makes it impossible to diverge silently.
- **Trigger:** **D20 is amended to name U6.2 or a successor package for the settings panes'
  live-region semantics — OR `pane-chrome.test.tsx`'s "PaneNote IS Banner's recipe" block reds,**
  which proves the duplication has started costing something and makes the fold the cheaper
  repair. Either is observable without re-deriving anything: the first is a plan diff, the second
  is a red test naming itself. Folding also requires `Banner` to grow an optional `id` and a
  documented politeness escape, and `MediaCapturePane`'s two `"Warning: "` / `"Note: "` prefixes
  to be dropped (Banner's `aria-label` prepends the severity, so they would read
  `"warning: Warning: …"`).

**Proposal 2 — no pressed treatment on any demo button**
- **Source:** `features/demo/ui/controls/button-recipe.ts` (no pressed arm);
  `features/demo/ui/screens/settings/SettingsNavBar.tsx` (the two buttons the phone fades).
- **What:** the phone's `SettingsNavBar` fades both its close and back buttons to
  `opacity: 0.6` while pressed (`:197-199`), and `Button` has the same. The demo has no pressed
  treatment anywhere. U6.2 built one for the settings ROW because A78 names its wash by value, and
  deliberately did not generalise it.
- **Why deferred:** a pressed state on a web button is `:active` (a stylesheet the demo forbids)
  or React state per control. Adding it to two buttons in one file is the per-file drift this
  campaign exists to delete; adding it to `buttonStyle` is a change to a W2 seam with ~45 call
  sites, in a package whose row does not name it.
- **Trigger:** **U8.3 (the last chrome package) or any package that opens
  `controls/button-recipe.ts` for a value change.** Concretely: grep `buttonStyle` for a
  `pressed`/`:active` arm — there is none today, and the decision is whether all ~45 sites get one
  together or none do. `SettingsCategoryList`'s `PRESSED_BG` is the recipe to generalise.

## 8. Two likely defects (asked for by the brief)

**Defect 1 — the settings row's pressed wash cannot be reached by a keyboard, and no test would
notice.** `PRESSED_BG` is driven by pointer events only. A keyboard visitor tabbing to a row and
pressing Enter or Space gets the activation and no visual acknowledgement at all — the phone's
`Pressable` fires its `pressed` state for both paths. This is not a regression (the demo had no
wash before) and it is not what A78 specifies, so it was not invented here; but it IS the shape
of DEF-UI-013's lesson — a state that exists for one input modality reads as working. The honest
fix is `:focus-visible`, which needs a stylesheet. **Watch:** any package adding keyboard
affordances to list rows, and any a11y review pass over the settings master list.

**Defect 2 — `PaneGroup`'s header row lost its `gap: 10`, and the case that gap covered is
invisible to jsdom.** The phone's `settingHeader` has no gap and neither does this now — faithful.
But `space-between` with a long label and a live value has no separation at all when the label
fills the row, and `vitest.config.mts:31` sets `css: false`, so jsdom performs no layout and no
test in this repo can see two elements touch. Today only `MediaCapturePane`'s Photo Quality passes
a `value`, and "Photo Quality" + "90%" has room to spare in 378px. **Watch:** the second
`PaneGroup` to take a `value`, especially one with a long label — it will look like that pane's
bug. The phone has the identical exposure at 390–430pt, which is why the gap was removed rather
than kept.

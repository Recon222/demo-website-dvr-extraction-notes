## 1. REFUTATIONS — verified against source first, as the brief requires

Seven claims in the plan, the matrix, the brief and U5.1's consume-me did not survive contact with
the phone or the tree. Each is refuted with `file:line`, and each refutation that could regress
silently is **pinned**.

### R1 — The filters glyph is NOT two-state, and `MAP_GLASS_COLORS.primaryLight` is not its reader

Plan §5's U5.2 row: *"filters `options-outline` 20px — **keeps reading
`MAP_GLASS_COLORS.primaryLight`** … when the badge count is >0, else `textSecondary`; that key's
**only** reader is this glyph, so do not inline it and do not orphan it."* U5.1's §10 consume-me
repeats it, and U0.1's row (plan `:249`) says the same.

**The phone's glyph is unconditional:**

> `MapControls.tsx:177` — `<Ionicons name="options-outline" size={20} color={textPrimary} />`

`textPrimary` is `isDark ? Colors.dark.text : Colors.light.text` (`:98`). There is no
`filterBadgeCount`-driven colour anywhere in the component; the count drives the badge's
*presence* (`:178`) and the button's *label* (`:171-175`), nothing else.

The two-state rule that got attributed to it belonged to the demo's **Clear pill**, which #127
deleted — and the citation gives it away: all three documents cite **`MapControls.tsx:234`**,
which at `ede8726` reads

```
color: activeFilterCount > 0 ? MAP_GLASS_COLORS.primaryLight : MAP_GLASS_COLORS.textSecondary,
```

i.e. the `clear-filters-button`'s colour line. Ported the phone. The glyph takes
`MAP_GLASS_COLORS.text`.

**Consequence, handled:** `primaryLight` loses its only reader. It is **kept**, not deleted,
because matrix row 18 names its next one — *"`accent = '#4ba3d4'` (`CaseMapPicker.tsx:29`) is
`MAP_GLASS_COLORS.primaryLight` un-imported"* — and U5.4 owns that file. It sits in
`MAP_GLASS_DERIVED_KEYS`, i.e. deliberately **unanchored**, so plan §6.6 gate 1 (which bans
*anchoring* a token with no web-side consumer) does not bite. The docblock is re-pointed and
offers U5.4 the alternative explicitly.

### R2 — `zIndex 1020` is not portable, and the row contradicts itself

Plan §5 / matrix A81: *"Outer `zIndex 1020` (**within the demo's own scheme — do not import the
phone's 1000-series; see D14**)"*. `1020` **is** the phone's 1000-series (`MapControls.tsx:242`,
`// Layout.zIndex.sticky`), so the parenthetical negates the value it qualifies. D14 rules the
demo's five z-schemes OUT of scope.

Measured in `screens/map/` at `ede8726`: `MapBottomSheet` **20** · `MapCanvas` error overlay **25**
· `CaseMapPicker` **30** · `CallConfirmSheet` **48** · `DemoNotification` **60**. `1020` would put
the floating chrome above every one of them — including the notification that reports proximity
failure. **Kept the demo's 15**, pinned, probe P4.

### R3 — The `paddingTop: 28` clause is phone history, and `top: 92` is not the demo's answer either

`partner-legwork-w3.md` W3-C3 already refuted the first half (the demo has no `paddingTop`), and
its proposed re-wording — *"the demo's `top: 92` absolute container becomes the phone's
`paddingHorizontal 12 / paddingTop spacing.sm / gap spacing.sm` inner row"* — is only half right:
it drops `paddingTop: safeAreaTop`, which is the outer container's whole job (`:107`).

The demo's `safeAreaTop` is a real, fixed thing: **PhoneFrame's status bar is `height: 50`**
(`PhoneFrame.tsx:100`), painted at `zIndex: 20` above the screen slot. So the faithful port is
`top: 0` + `paddingTop: 50 + spacing.sm` = **58**, which is also what the old `92` decomposed into
(50 + the Change Case pill at `top: 58` + its ~29px height + a gap). With the pill deleted, the
clearance goes with it and the bar moves **up 34px**. Pinned, probe P3.

### R4 — `filterBadgeCount` is per-STATUS, not `countActiveFilters`

The plan says only *"a count badge"*. The phone is specific:

> `MapHost.tsx:268` — `const filterBadgeCount = (filters.statuses?.length ?? 0) + (proximityIsActive ? 1 : 0)`

and its own test exists to separate that from the demo's `countActiveFilters` shape:

> `MapHost.test.tsx:490-521` — *"THREE statuses, deliberately. `activeFilterCount` counts the
> status *group* as one plus searchText as one … correct `statuses.length (3) + proximity (1) = 4`;
> regressed `activeFilterCount (2) + proximity (1) = 3`. With two statuses both arms land on 3 and
> the test pins nothing."*

The demo's `countActiveFilters` (`mapFilters.ts:67-72`) is the slot count **and** includes search
text, so it is wrong twice over. `MapScreen` now derives the badge separately; `countActiveFilters`
keeps its own job (deciding whether a filter is what emptied the sheet, MR-3).

### R5 — D-3 does not fire: U5.2 needs no `MAP_SURFACE_COLORS.inputBg`

U5.1's deferral D-3: *"**U5.2 is the near-certain case** — the collapsed search bar's field and
filters button are `MAP_SURFACE_COLORS.inputBg`-shaped on the phone."*

They are not. `MapControls.tsx:135` paints the search pill with `backgroundColor: surfaceBg`, which
is `MAP_GLASS_COLORS.containerBg*` (`:96`); the close button takes the same (`:121`) and the inline
buttons are transparent. `inputBg` appears nowhere in the component. That is the phone's own "one
surface" rule — the same rule that had `inputBgDark`/`inputBgLight` deleted in `6e10eea3`.
**No key added.** D-3 stays open for whichever surface actually needs one; it is not this one.

### R6 — Row 43 is unbuildable in U5.2, and the phone's own value fails its floor

Two independent findings, both new:

1. **The demo cannot paint a placeholder colour at all.** The phone passes
   `placeholderTextColor={placeholderColor}` (`MapControls.tsx:143`, from `Colors.dark.textTertiary`
   at `:100`). The web spells that `::placeholder`, which needs a **stylesheet rule**, and
   `ui/demo.css` is **U8.2's alone** — plan §6.1: *"If a package thinks it needs to touch it, that
   is a scope error."* U2.1 hit this first and made the same call
   (`tokens/field-input.ts:44-47`). There is no inline route to a pseudo-element.
2. **When U8.2 does paint it, `textTertiary` is the wrong value.** Measured with
   `palette-contrast.test.ts`'s own helpers: `colors.textTertiary #7a9fc4` on
   `MAP_GLASS_COLORS.containerBg` over a white tile = **3.06** — under row 43's own **3.79** M2b
   floor, never mind 4.5. Row 43's escape clause is written for exactly this: *"If it lands below
   3.79 the placeholder must take `textSecondary`"*. `#99badd` measures **4.21** and clears it.

Row 43 therefore stays `it.todo`, **re-owned to U8.2**, with both numbers and the seam recorded
in-file so nothing is re-derived. Row 45 is re-owned to **U5.3** for the same structural reason
(U0.5's "pin the ratio AT the constant" cannot precede `MapFiltersSheet`'s section-label constant).

### R7 — `MAP_GLASS_COLORS.clearActiveBg` had to go, and U5.1 said so

U5.1 shipped it derived with *"U5.2 deletes this key's one reader with the Clear pill"*. Deleted,
along with its `MAP_GLASS_DERIVED_KEYS` entry. That list is **membership**, not anchors, so the
drift guard stays at **143 rows** (verified, exit 0). The collapsed chrome has no active-filter
wash: the active state is the badge.

## 4. Deviations from the phone, each named

1. **Badge fill is `primaryDark`, not `primary`** — D5's amendment, A19's rider, §C.1 row 41. The
   phone genuinely ships `#ffffff` on flat `primary` = **3.73:1** under a NUMERAL
   (`MapControls.tsx:181`, `:328`; `partner-legwork-w3.md` §1.3 verified it independently). Exported
   as `MAP_FILTER_BADGE_FILL` so the contrast pin sits at the painted constant. **The PR body must
   say, in these words, that the phone ships the 3.73 pairing and the demo deliberately does not.**
2. **`onOpenFilters` is OPTIONAL where the phone's is required** (`:47`). See §5 — the largest
   design decision in the package.
3. **`role="status"` on the chip summary.** The phone has no live region. The demo's deleted count
   pill had one (review R-7a: *"this pill is the ONLY feedback the filter, search and proximity
   controls give"*), and the chip is the surface that inherited its "N of M". Kept the promise, not
   the pill.
4. **`onProximityDeactivate={handleProximityToggle}`** — the toggle passed whole rather than split.
   The chip renders under `proximityActive &&`, so only the OFF branch is reachable. Splitting it
   would strand the anchor chain and its R-18a notice with no caller for one package and then
   re-add them.
5. **No `isDark` / `safeAreaTop` props.** `MAP_GLASS_COLORS` is `[scheme]`-indexed after U5.1 (plan
   §9 clause 12's shape), and the demo's status bar is a fixed 50 rather than an inset — a prop with
   one constant caller is scaffolding.
6. **The chip's `locate-outline` mark measures 2.27:1** on the chrome over a white tile. Recorded,
   not hidden, and not a 1.4.11 violation: it is `aria-hidden` and the chip's own text carries every
   bit of its meaning, which is the exemption 1.4.11 states. If a device pass says it disappears,
   the fix is `colors.primaryLight`, not a new token.

## 5. The design decision this package turns on, and what was rejected

**Problem.** U5.2 deletes the controls; U5.3 builds their destination. Between the two, `MapScreen`
has nowhere for a filters button to go.

**Chosen:** `onOpenFilters` is optional and gates the divider, the button and the badge; the chip
body degrades from a `<button>` to a `<div>` readout while its ✕ stays live. `MapScreen` omits the
prop. This is the repo's own §49a rule, cited three times in the very file being edited
(`MapScreen.tsx:58-68`): *"a mount without a handler simply has no button, rather than a button that
swallows every press"* — the gate `onChangeCase`, `onGoToLocation` and `onExportMap` already use.
U5.3's wire-up is one line.

**Rejected — a required prop wired to a no-op.** Phone-exact in shape, but it ships an affordance
that lies, which is the one thing this demo's honesty rule forbids outright.

**Rejected — a required prop wired to a "map filters are coming" notice.** Scaffolding copy that
ships in the wave PR if U5.3 slips, and invents product voice for an unfinished port.

**Rejected — U5.2 building a placeholder sheet.** U5.3 owns `MapFiltersSheet`; building UI so a test
can pass is the anti-pattern `palette-contrast.test.ts:723-739` already refuses by name.

**Rejected — keeping the old pills alive under the new bar until U5.3.** The B-row deletion is
owner-ruled, and a second control set under a phone-exact bar is neither state.

**The cost, stated plainly.** For exactly one package, status filters, the four radius presets and
Clear-all are unreachable from the UI. Search, proximity-by-long-press, the chip exit and the
sheet's own Clear route all stay live. **And one more, found by pinning it rather than by
argument:** without `NEXT_PUBLIC_MAPBOX_TOKEN`, `MapCanvas` returns `[data-map-fallback]` *before*
the `[data-map-canvas]` surface, so there is nothing to long-press and proximity is unreachable
entirely — where the deleted toggle pill used to work token-less through the anchor chain's
`DEFAULT_MAP_CENTER` arm. U5.3's sheet Toggle restores it token-less. Pinned in
`MapScreen.test.tsx`, probe P13. **This is inherent to the plan's own U5.2 → U5.3 split** —
U5.3's row calls itself *"the destination for everything U5.2 deleted"* — not a choice this package
made.

## 9. Successor note — `SEAM(U5.3)`, and one for U5.4 / U8.2

Grep `SEAM(U5.3)`; two sites carry it (`MapControls.tsx`'s `onOpenFilters` prop docblock and
`MapScreen.tsx`'s render).

**U5.3 — your wire-up is one line, and then eight todos are yours:**

```tsx
onOpenFilters={() => setFiltersVisible(true)}
```

- Pass it to `MapControls` and the divider, the filters button and the badge appear, and the chip

- **`onClearAll` clears the filters AND deactivates proximity** — the phone's own contract
  (`MapHost.test.tsx`, *"onClearAll clears the filters AND deactivates an active proximity ring"*).

- **The eight `it.todo`s to un-todo**, all in `MapScreen.test.tsx` unless noted:

## 13. Two likely defects (where I would look first)

1. **`MapScreen` computes a badge count that nothing renders, and probe P7 proves nothing catches
   it.** The moment U5.3 passes `onOpenFilters` the number becomes visible — and if U5.3 also
   "tidies" the derivation onto `countActiveFilters` (which is right there, one line above, already
   imported, and named plausibly), the badge will read 3 where the phone reads 4 and every gate will
   stay green. The phone built a three-status fixture specifically to separate those two
   expressions; the demo currently has no equivalent. **This is the single highest-value un-todo in
   §9's list, and it should land in U5.3's first commit, not its last.**
2. **The geometry pin reads `container.firstElementChild`, which is positional.** Probe P6
   demonstrated it: smuggling any element in ahead of the inner padding div reds the `paddingTop`
   assertion for a reason that has nothing to do with padding. It fails loud and in the right
   direction, so it is not wrong — but the next person to add a sibling (a scale bar, a
   compass, an attribution shim) will read a confusing failure and may "fix" it by loosening the
   query to `querySelector('div')`, which pins nothing. If that block is touched, give the inner row
   its own `data-testid` rather than widening the selector.

Second-order, worth one sentence: **the chip body silently changes element type** between the gated
and ungated states (`<button>` ↔ `<div>`). It is pinned (probe P11), and it is the honest shape —
but any future code that does `chip.querySelector('button')` expecting the body will find the ✕
instead.

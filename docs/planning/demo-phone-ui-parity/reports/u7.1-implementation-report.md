## 3. Design decisions, with the alternatives rejected

### D-1 — `palette[TERMINAL_SCHEME]`, not `colors`, not `palette.dark`

The phone wraps the terminal in `<ForceColorScheme scheme="dark">` (`ImportTerminalProgress.tsx:343`)
and then writes `Colors.dark.*` in the palette module, explaining at `:14-18` that reading those tokens
through `useTheme()` inside the forced subtree returns exactly the dark values. The demo has no theme
context, so the forced scheme has to be written down. Three ways:

| Option | Verdict |
|---|---|
| **(a) `colors.*`** | **REJECTED.** `colors` is `palette[scheme]`, the APP scheme, and §9 clause 12 makes flipping it a one-site change. The day light opens, this puts light-theme grey `#4b5563` on a near-black console ground. Smallest diff; silently wrong in the future the plan explicitly keeps open. |
| **(b) `palette.dark.*`** | **REJECTED.** The phone-literal spelling, and forbidden outright by the scheme-half scan (r1 F18 / r2 F24, four SURVIVED probes behind it). |
| **(c) `export const TERMINAL_SCHEME = 'dark'` + `palette[TERMINAL_SCHEME]`** | **TAKEN.** The demo's expression of `ForceColorScheme`; guard-clean; the only one of the three still correct after a flip. |

The same reasoning splits the file: **inside** the phone's forced-dark subtree everything reads
`TERMINAL_PALETTE`; **outside** it (headline, progress track, outcome badge/CTA) everything reads
`colors.*` and *should* follow a flip. That is the phone's own boundary, not a preference.

`screen` keeps the phone's `{ light, dark }` fork because `NotesScreen` needs the light arm
(`NotesSectionEditor.tsx:105` reads `screen[colorScheme]`), and it is indexed with `scheme` there —
the panel shade follows the app, everything inside the panel does not.

**The scan trap this avoids:** `TERMINAL_PALETTE.screen.dark`, the phone's own spelling at its `:347`,
matches the scheme-half regex `X.dark` and would red the guard. `screen[TERMINAL_SCHEME]` is the same
value, guard-clean, and semantically exact.

### D-2 — no `term` palette prop on `TerminalLine`

The phone passes the palette subset down as a prop and gives its reason
(`TerminalLine.tsx:41-44`: *"kept as a prop rather than imported directly so the row stays a pure
presentational component that can be rendered against any palette in a test"*). **Not copied.** D20's
carve-out grants prop-signature changes only to the six packages that name them and U7.1 is not one;
and the row is `memo`-wrapped with an append-only render contract (its docblock `:15-18`), where a
module import keeps every style object module-level and referentially stable for free. The phone's
stated benefit — test-injectable palettes — is bought instead by importing the module in the test.

### D-3 — thirteen `BANNED` entries, and NOT a `RETIRED` append

Banned: the thirteen console shades the module now owns. Two (`#060a12`, `#141c28`) had a measured
second owner (R5); the rest are near-black navies and console greys that exist nowhere else, so none
can be reached for innocently — the same test U2.4's recessed-well entries pass. Deliberately **not**
banned: `#4BA3D4`, `#99badd`, `#ffd93d`, `#10d177`, `#ff4757` — the module reads all five from
`palette[TERMINAL_SCHEME]`, each is live in 15–44 files, and banning them is the full 1,144-literal
sweep D3 ruled against.

**Rejected:** appending the three retired values to `tokens/__tests__/palette.test.ts`'s `RETIRED`
list. It would catch a revert of the AA raise (its scan covers token modules too), but that revert is
already caught twice and more informatively — by the ratio assertions (which name the failing ratio)
and the `toEqual` shape pin. A third mechanism over one file is list maintenance without coverage.

### D-4 — comments are code to the banned-literal scan

Three prose mentions of `#060a12` / `#0a0f18` / `#141c28` in docblocks were real offenders: the BANNED
scan reads **raw** text (only the scheme-half scan calls `stripComments`). All three now name the token
instead, which is the documentation the ban is asking for. Same treatment applied pre-emptively to the
retired teal so U8.2's future scan has nothing to trip over (`7b2a329`).

## 8. Two likely defects (where a reviewer should look hardest)

1. **The `vi.doMock` flip pin could couple test files.** `terminal-palette.test.ts`'s clause-12 pin calls
   `vi.resetModules()` and mocks `@/features/demo/ui/tokens/palette`. It unmocks and resets in a
   `finally`, and the file is green solo and in the full run — but module-registry mutation inside a
   worker is the kind of thing that bites under a different file order or a `--no-isolate` run. If a
   sibling test in the same worker starts failing on palette identity, this is the first suspect. The
   containment is that the mock affects only **dynamic** imports after the reset; every other file's
   static imports are already bound.
2. **`ImportTerminalProgress.test.tsx`'s live-dot selector is structural.** It finds the dot via
   `[data-testid="terminal-trust-line"]`'s `previousElementSibling` because the dot is `aria-hidden`
   with no test id of its own. It kills the mutation it is aimed at (P1), but it is coupled to the title
   bar's DOM order: U7.2's `OverlayHeader` consolidation does not touch this surface, but any future
   reshuffle of the title-bar right group would break the pin in a way that reads as a false red rather
   than a real regression. A `data-testid` on the dot would be the robust fix; it was not added because
   adding a test id to production markup for a pin's convenience is the thing the reviewer contract
   flags, and the phone has none either.

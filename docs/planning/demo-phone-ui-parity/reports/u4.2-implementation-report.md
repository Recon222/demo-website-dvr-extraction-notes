## 3. Decisions

1. **`SettingsModal` consumes the scrim + sheet SEAM, not `ModalShell`** — the second of the two
   options plan §5's U4.2 row offers, recorded here as the row requires. Its docblock's reason
   survives contact with the port: that sheet swaps between a master bar and a pushed detail bar
   with its own back affordance (`SettingsNavBar`), so wrapping it in `ModalShell` means either two
   stacked headers or a "custom header" escape hatch on a component eight other modals depend on.
   What was duplicated was never the header — it was the chrome, and the chrome is now imported.
   *Rejected:* a `header` render-prop on `ModalShell` (the escape hatch, on the highest-leverage
   recipe in the codebase, for one caller).

2. **The hit target is real padding plus an equal negative margin.** `ModalHeader.tsx:67-70` paints
   a 32-square frame and takes the HIT area to 52 with `hitSlop={10}`, and its comment says why: a
   real 44 frame would grow the header 20px. A49/DEF-UI-019's web ruling is *"real padding or a
   pseudo-element"*, and an inline `CSSProperties` object cannot write a pseudo-element — so
   `padding: 14` IS the hit area (24 + 28 = 52) and `margin: -10` (the phone's own hitSlop number)
   returns the 32-square box to the flex row. Layout is unmoved to the pixel: the margin box is 32
   either way and the glyph is centred in it. *Rejected:* `padding: 4` alone (a 32px target, under
   the 44 floor) and a real 52 frame (grows every one of the nine headers).

3. **`highlightTop` and `innerShadow` are not painted.** `ModalHeader.tsx:52` reads the tier and
   spends exactly `gradient` and `border`. U1.4 drew this line for the header tier
   (`header-chrome.ts:20-35`) and U4.1 for the sheet tier; three packages, one finding.

4. **The header row is flat, and one wrapper div goes.** The phone flexes the title
   (`ModalHeader.tsx:92`), which is why its bar needs no `justifyContent`. The demo's
   `space-between` around a nested left group reproduced that with two more nodes.

5. **One shared glyph-button fragment for close AND back.** Two different treatments for two
   identical idioms is more code, and the back chevron was a bare 24-square target.

6. **The border is spelled in longhands** — `borderBottomStyle` / `borderBottomWidth` /
   `borderBottomColor`, per the lit-edge ruling §1 (`reports/partner-lit-edge-ruling.md`), adopted
   mid-package on the coordinator's instruction. This bar has one edge and no lit top, so it has no
   highlight to lose; the reason to spell it out anyway is that a `borderBottom:` shorthand is the
   slot that turns a consumer's `{ ...modalHeaderBar, borderBottomColor: X }` into React's
   `conflicting property` path on paint 2. Pinned by a negative control (probe P11).

7. **The reduced-motion gate.** See §6 — a deliberate deviation, not in the row.

## 6. Deviations from the row

**One, deliberate: the reduced-motion gate (commit `8ca8a1a`).**

`modalSheet` carried `animation: 'screenIn 0.3s ease'` unconditionally, so **nine** surfaces — this
shell's eight callers plus the Settings sheet — slid in for visitors who had asked them not to,
while every other inline-styled motion in this feature gates on `useReducedMotion`
(`features/demo/CLAUDE.md`; plan §4.7). U4.1 fixed the identical defect on the three picker sheets
and called it *"a behavioural fix, not a restyle"*.

It is in this package because the commit before it made it a **one-site** fix; before the chrome
collapse it was two unconditional copies in two files. It is not in the U4.2 row, so it is one
commit and reverts cleanly if the reviewer disagrees.

Two things it dragged in, both recorded rather than hidden:

- **`SettingsModal` swaps `motion/react`'s `useReducedMotion` for `@/lib/hooks/use-reduced-motion`.**
  Measured, not preferred: with `motion/react`'s hook the Settings sheet **kept animating** under a
  `reduce` stub, because that hook caches its `matchMedia` subscription module-globally — the exact
  trap `import/PickerStage.tsx:94` records. Its pane-transition gate was structurally unobservable
  to a test. It is now the same hook `ModalShell` and `GlassBottomSheet` use.
- **One pin updated, in the same commit, and not weakened.**
  `SettingsModal.test.tsx`'s `expect(renderPane).toHaveBeenCalledTimes(1)` reddened
  (`expected "vi.fn()" to be called 1 times, but got 2 times`) because
  `lib/hooks/use-reduced-motion.ts:13-23` returns `false` on the first render and corrects from an
  effect, so a mounted component renders twice. The line's own comment says *"exactly one pane is
  ever asked for"*, so it now asserts the **set of ids** requested — which is the contract, and
  which a call count could never express: it was equally green over one call for the *wrong* id.

- **`closeAccessibilityLabel` is required and must be UNIQUE among open dialogs.** Two controls with

  library · Close case actions · Close user profile*.
- **`modalScrim` + `modalSheet` are the page-sheet chrome.** Spread them; override `zIndex` if you

- **`modalHeaderBar` carries no `border` / `borderColor` / `borderBottom` key** and must not gain

- **The ground is `colors.background`, pinned.** Do not re-point it at `colors.modal` or at A38's

**1. `GLASS_TIER.dark` cannot be caught by any test today — a FOURTH file joins the hole.**

- **Source:** U4.2 probe P2 (SURVIVED); U1.4 probe P10 / its §6 D-2; U4.1 probe P2; W1 review F18.
- **What:** Mutating `GLASS_TIER[scheme]` to `GLASS_TIER.dark` in `_shared.tsx`'s `modalHeaderBar`
  leaves the suite fully green — the demo renders `dark` and the values are byte-identical. Every
  seam module built on the two-scheme records has this hole; this package adds `_shared.tsx` to
  `glass-tokens.ts`, `header-chrome.ts` and `sheet-chrome.ts`.
- **Why deferred:** The only honest kill is to render a light surface, which plan §9 clause 12
  already schedules. A source-text assertion would be the string-presence anti-pattern.
- **Trigger:** §9 clause 12's scratch-worktree scheme flip at U8 exit — if the modal headers do not
  turn light with everything else, this is why. Or earlier, if any package ships a light surface.
  (Unchanged from U4.1's proposal 1; this is a fourth instance of the same row, not a new one.)

**2. `ModalHeader`'s leading icon slot is not built.**

- **Source:** U4.2 R-4; matrix A60's Delta (*"leading 24px icon at `colors.primary`"*);
  phone `ModalHeader.tsx:29,62`.
- **What:** `ModalShell` takes no `icon` prop, so the demo's profile editor header shows a title
  where the phone's shows `person-circle-outline` + title. The other seven callers port
  `case-management` page sheets whose headers carry no glyph, so they are already correct.
- **Why deferred:** One liftable value against seven invented ones. `ModalHeader`'s other four
  consumers are agency-cloud modals, which plan §2 excludes, so the demo will never have more than
  one honest caller unless a later package adds a surface that does.
- **Trigger:** U6.1 or U6.2 opening `settings/UserProfileModal.tsx` — the change is an optional
  `icon?: ReactNode` rendered before the title stack, plus a `person-circle-outline` SVG in
  `settings-icons.tsx` (whose `stroke="currentColor"` pattern demo §3.5 already calls the right
  one). If U6 declines it, it must be raised again before U8 exit, because A60 is a Tier-A row and
  §9 clause 3 requires it COMPLETE or carrying a ratified divergence.

**3. `useReducedMotion` applies one frame of motion before it corrects.**

- **Source:** U4.2 §6; `lib/hooks/use-reduced-motion.ts:13-23`.
